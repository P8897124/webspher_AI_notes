# IBM WebSphere Network Deployment (ND) on Linux
## End-to-End Three-Server Installation, Federation and Cluster Configuration SOP

**Document purpose:** Provide an operational procedure for building a three-server IBM WebSphere Application Server Network Deployment environment on Linux using offline installation media.

**Operating approach**
- IBM Installation Manager and WebSphere product installation: CLI
- Profile creation: CLI
- Node federation: CLI
- DMGR, Node Agent and application-server process startup: CLI
- Cluster creation and cluster-member configuration: **DMGR Administrative Console (GUI)**
- IHS and web-server integration: **out of scope; to be documented separately**

> **Version control:** This SOP includes command patterns for WAS 8.5.5 and WAS 9.0.5. Select one approved WAS version and fix-pack level for the build. Do not mix repositories from different versions. Confirm exact package IDs, supported Linux releases, Java SDK level and fix-pack prerequisites against IBM documentation for the selected release before executing.

## 3. Linux prerequisites on all three servers

Complete these checks before installing WebSphere.

### 3.1 Confirm operating system and architecture

```bash
cat /etc/os-release
uname -r
uname -m
hostname
hostname -f
```

Check the exact Linux distribution, release, architecture and WAS fix-pack combination against IBM's system requirements and support matrix.

### 3.2 Verify hostname and DNS resolution

```bash
hostname -f
getent hosts wasdmgr01.example.com
getent hosts wasapp01.example.com
getent hosts wasapp02.example.com
```

Confirm forward and reverse DNS resolution with the infrastructure team. The configured hostnames must resolve consistently from all three servers.

### 3.3 Check CPU, memory and filesystems

```bash
lscpu
free -h
df -hT
lsblk
```

Confirm sufficient capacity for product binaries, profiles, application files, logs, JVM dumps and expected operational growth. Final sizing should be based on the application workload and approved capacity plan, not generic example values.

### 3.4 Check Linux resource limits

```bash
ulimit -a
```

Review open-file, process and memory limits with the Linux team. Configure them according to IBM requirements and organizational standards.

### 3.5 Create a dedicated WebSphere service account

Example commands (run with approved Linux administrator privileges):

```bash
useradd -m -s /bin/bash wasuser
passwd wasuser
```

Create required directories and assign ownership:

```bash
mkdir -p /opt/install
mkdir -p /opt/IBM/WebSphere
mkdir -p /opt/IBM/IMShared

chown -R wasuser:wasuser /opt/install
chown -R wasuser:wasuser /opt/IBM
```

Use the approved WebSphere service account consistently for product installation and profile administration. Follow organizational access, ownership and privilege policies.

### 3.6 Check time synchronization

```bash
timedatectl
```

Ensure all three servers use the approved time source.

### 3.7 Firewall and port checks

Do not disable the host firewall. Obtain approval for only the required source, destination and port combinations.

Check listening ports:

```bash
ss -lntp
```

After the DMGR profile is created, test connectivity from each application node to the actual DMGR SOAP connector port:

```bash
nc -zv wasdmgr01.example.com 8879
```

`8879` is a common default SOAP connector port, not a guaranteed value. Verify the actual configured port from the DMGR profile before testing or requesting firewall changes.

## 6. Install WebSphere ND binaries offline

Install WAS locally on each of the three servers. Each machine needs its own product binaries to run its local WebSphere processes.

Change to the Installation Manager command-line tools directory:

```bash
cd /opt/IBM/InstallationManager/eclipse/tools
```

### 6.1 List available packages

For a WAS 9.0.5 repository:

```bash
./imcl listAvailablePackages \
  -repositories /opt/install/WAS_ND,/opt/install/JAVA_SDK
```

For a WAS 8.5.5 repository:

```bash
./imcl listAvailablePackages \
  -repositories /opt/install/WAS_ND
```

Review the output and confirm the exact offering IDs and versions present in the offline repositories. Do not assume that an SDK or fix pack is included unless it appears in the package listing.

### 6.2 WAS 9.0.5 installation pattern

After confirming that both offerings are present in the repositories:

```bash
./imcl install \
  com.ibm.websphere.ND.v90 \
  com.ibm.java.jdk.v8 \
  -repositories /opt/install/WAS_ND,/opt/install/JAVA_SDK \
  -installationDirectory /opt/IBM/WebSphere/AppSrv01 \
  -sharedResourcesDirectory /opt/IBM/IMShared \
  -acceptLicense \
  -showProgress \
  -log /opt/install/was_install.log
```

### 6.3 WAS 8.5.5 installation pattern

For a new 8.5.5 installation where Java 8 is supported and selected for the chosen maintenance level:

```bash
./imcl install com.ibm.websphere.ND.v85 \
  -repositories /opt/install/WAS_ND \
  -installationDirectory /opt/IBM/WebSphere/AppSrv01 \
  -sharedResourcesDirectory /opt/IBM/IMShared \
  -properties user.wasjava=java8 \
  -acceptLicense \
  -showProgress \
  -log /opt/install/was_install.log
```

For WAS 8.5.5, verify the exact repository contents, Java selection and maintenance-level requirements before using this command. This is a version-specific command pattern, not a substitute for checking the downloaded repository.

Run the applicable version-specific installation command locally on:

## 7. Create the Deployment Manager profile on Server 1

Log in to Server 1 (`10.10.10.10`) as the WebSphere service account.

```bash
cd /opt/IBM/WebSphere/AppSrv01/bin

./manageprofiles.sh -listProfiles
```

Create the DMGR profile:

```bash
./manageprofiles.sh -create \
  -profileName Dmgr01 \
  -profilePath /opt/IBM/WebSphere/AppSrv01/profiles/Dmgr01 \
  -templatePath /opt/IBM/WebSphere/AppSrv01/profileTemplates/management \
  -serverType DEPLOYMENT_MANAGER \
  -cellName ProductionCell01 \
  -nodeName DmgrNode01 \
  -hostName wasdmgr01.example.com
```

This creates:

- Profile: `Dmgr01`
- Cell: `ProductionCell01`
- Node: `DmgrNode01`
- Deployment Manager process: `dmgr`

Verify:

```bash
./manageprofiles.sh -listProfiles
ls -l /opt/IBM/WebSphere/AppSrv01/profiles/Dmgr01
```

Review profile creation logs under:

```text
/opt/IBM/WebSphere/AppSrv01/logs/manageprofiles/
```

## 8. Start the DMGR and identify its SOAP port

Start the Deployment Manager:

```bash
cd /opt/IBM/WebSphere/AppSrv01/profiles/Dmgr01/bin

./startManager.sh
```

Check the process and log:

```bash
ps -ef | grep -i dmgr

tail -100 \
  /opt/IBM/WebSphere/AppSrv01/profiles/Dmgr01/logs/dmgr/SystemOut.log
```

Wait for the DMGR to reach its ready state.

Find the configured SOAP connector port:

```bash
grep -n -A 5 -B 5 "SOAP_CONNECTOR_ADDRESS" \
  /opt/IBM/WebSphere/AppSrv01/profiles/Dmgr01/config/cells/ProductionCell01/nodes/DmgrNode01/serverindex.xml
```

Record the actual port. `8879` is a common default only. Use the configured value in federation commands and firewall requests.

The DMGR console HTTPS port is commonly `9043`, and HTTP is commonly `9060`; verify actual values in the profile configuration before connecting.

Log in to Server 2 (`10.10.10.11`) as the WebSphere service account.

```bash

  -profileName AppSrv01 \

  -templatePath /opt/IBM/WebSphere/AppSrv01/profileTemplates/managed \
```

Replace `8879` with the actual DMGR SOAP port found in Section 8.

If administrative security is enabled, provide the authorized DMGR credentials using the supported `addNode.sh` options for the installed WAS version. Avoid placing production passwords in shell history, scripts or logs; use the organization's approved secure credential-handling method.

Wait for federation to complete successfully.

### 9.2 Verify Server 2 federation

```bash
ps -ef | grep -i nodeagent

tail -100 \
  /opt/IBM/WebSphere/AppSrv01/profiles/AppSrv01/logs/nodeagent/SystemOut.log
```

The Node Agent is configured for the federated node and can be managed by the DMGR.

## 12. Create the cluster and cluster members from the DMGR Administrative Console

**This section is GUI-based. Cluster creation and member creation are not performed using `wsadmin` or CLI in this SOP.**

The cluster will be named **`cluster`**.

### 12.1 Open the DMGR Administrative Console

From an approved workstation, open:

```text
https://wasdmgr01.example.com:9043/ibm/console
```

`9043` is a common default HTTPS console port. Confirm the actual port in the DMGR profile. Use the approved administrator account and complete any required certificate/trust steps under your organization's security policy.

### 12.2 Navigate to the cluster configuration page

In the DMGR console, navigate to:

**Servers → Clusters → WebSphere application server clusters**

Click **New** to start the cluster creation wizard.

### 12.3 Enter the cluster name

Enter:

```text
cluster
```

Choose the appropriate cluster configuration options presented by your WAS version and organizational design. For a conventional two-member application cluster, use the standard cluster configuration unless the architecture requires a specific setting.

Proceed to the next wizard page.

### 12.4 Add the first cluster member

Enter the first member details:

| Setting | Value |
|---|---|
| Member name | `AppSrv01Member` |
| Node | `AppNode01` |
| Weight | Use the approved initial/default value |
| Generate unique HTTP ports | Select |

The member must be assigned to `AppNode01`, which is hosted on Server 2.

### 12.5 Add the second cluster member

Add another member:

| Setting | Value |
|---|---|
| Member name | `AppSrv02Member` |
| Node | `AppNode02` |
| Weight | Use the approved initial/default value |
| Generate unique HTTP ports | Select |

The member must be assigned to `AppNode02`, which is hosted on Server 3.

**Important:** Confirm that the two members are on different nodes. Selecting **Generate unique HTTP ports** helps avoid port conflicts between members; still review the generated port assignments and compare them with the organization's port plan.

### 12.6 Finish and save

1. Review the cluster and member summary.
2. Click **Finish**.
3. Click **Save** in the Administrative Console when prompted or when the unsaved-changes indicator appears.
4. Review any synchronization messages.
5. Synchronize the managed nodes if required.

### 12.7 Verify cluster configuration

Navigate to:

**Servers → Clusters → WebSphere application server clusters**

Confirm that the cluster named `cluster` exists and has these members:

| Cluster member | Node |
|---|---|
| `AppSrv01Member` | `AppNode01` |
| `AppSrv02Member` | `AppNode02` |

Also verify the member details under the cluster's member list and confirm that the port assignments are unique and approved.

### 12.8 Start the cluster

From:

**Servers → Clusters → WebSphere application server clusters**

Select `cluster` and use the **Start** action.

Monitor the cluster and member status. Confirm that both `AppSrv01Member` and `AppSrv02Member` reach the Started state.

If a member does not start, inspect that member's `SystemOut.log` and `SystemErr.log` on its host before retrying.

## 13. Deploy an application to the cluster (GUI)

Application deployment is not completed merely by creating a cluster. The application must be installed and mapped to the cluster.

In the DMGR Administrative Console:

1. Navigate to **Applications → New Application → New Enterprise Application**.
2. Browse to or provide the approved application archive (EAR, WAR, or supported package).
3. Follow the installation wizard.
4. When prompted for target mappings, select the cluster named `cluster` as the deployment target.
5. Review module-to-server mappings and virtual host settings as applicable to the application.
6. Complete the wizard.
7. Click **Save**.
8. Synchronize the managed nodes if required.
9. Start the application from **Applications → Application Types → WebSphere enterprise applications**.
10. Verify application status and test using the application's approved test method.

Use the application's deployment runbook for environment-specific datasource, JMS, security, class-loading, shared-library and application configuration. Do not invent these values during a generic platform build.

## 15. Important WebSphere profile concepts

A profile is a separate runtime configuration created from the installed WebSphere product binaries. Multiple profiles can use one product installation, but each profile has its own configuration and runtime directories.

| Profile type | Purpose |
|---|---|
| Deployment Manager | Central administration of a WebSphere ND cell |
| Custom | Creates an initially empty managed node intended for federation |
| Application Server | Creates an application-server runtime, commonly used as a standalone server |
| Cell | Creates a DMGR profile and an application-server node profile together as a combined profile-creation operation |
| Secure Proxy | Provides a secure proxy-server environment where the relevant product offering and version support it |

Key points:

- A DMGR profile contains the Deployment Manager process.
- A Custom profile does not automatically create an application server.
- After federation, the DMGR can centrally create application servers and cluster members on managed nodes.
- A standalone Application Server profile is not the same as a federated Custom profile.
- A Cell profile is not the topology used in this three-host procedure.
- Secure Proxy availability depends on the installed product offering and version.

## 18. Troubleshooting checklist

| Problem | What to check |
|---|---|
| Installation Manager fails | Installer package, permissions, disk space and IM logs |
| WAS installation fails | Repository path, offering ID/version, SDK compatibility, disk space and installation log |
| Profile creation fails | Template path, hostname, permissions and `manageprofiles` logs |
| DMGR does not start | DMGR `SystemOut.log`, `SystemErr.log`, Java, port conflicts and filesystem space |
| `addNode.sh` fails | DMGR availability, SOAP port, DNS, firewall, credentials, certificates and logs |
| Node Agent does not start | Node Agent logs, DMGR connectivity and node configuration |
| Node synchronization fails | SOAP connectivity, authentication, certificates and cell/node configuration |
| Cluster member does not start | Member `SystemOut.log` and `SystemErr.log`, port conflicts, JVM settings and node status |
| Application does not start | Application logs, deployment mappings, application configuration, datasource/JMS resources and JVM errors |

### 18.1 Important log locations

```text
DMGR:
  profiles/Dmgr01/logs/dmgr/

Server 2 Node Agent:
  profiles/AppSrv01/logs/nodeagent/

Server 3 Node Agent:
  profiles/AppSrv02/logs/nodeagent/

Application server member:
  profiles/<profile_name>/logs/<server_name>/
```

For startup failures, inspect `SystemOut.log`, `SystemErr.log` and `native_stderr.log` where present. Check timestamps and correlate them with the failed operation.

## 19. Interview questions and answers

### Q1. Why do we install WebSphere binaries on all three servers?

Each machine needs local WebSphere runtime binaries to execute its local DMGR or managed-node processes. The DMGR does not automatically install product binaries on remote machines.

### Q2. Why do we install Installation Manager on all three servers?

Installation Manager is the local tool used to install and maintain WAS product binaries. We can download its installer once and distribute it to all three servers.

### Q3. Can the DMGR create a Custom profile remotely on another server?

Not through ordinary DMGR administration. The Custom profile is created locally with `manageprofiles.sh` after local WAS binaries are installed. Profile creation and remote node administration are different operations.

### Q4. What is the difference between a Custom profile and an Application Server profile?

A Custom profile creates an initially empty managed node intended for federation. An Application Server profile creates an application-server runtime, commonly used as a standalone server.

### Q5. What happens when we federate a Custom profile?

The node joins the DMGR cell. A Node Agent is configured for the managed node. The DMGR can then centrally manage the node and create application servers and cluster members on it.

### Q6. What is a Cell?

A cell is a logical administrative grouping consisting of a DMGR and its federated nodes. One DMGR centrally manages the cell configuration.

### Q7. What is a Node?

A node is a logical grouping of WebSphere server processes associated with a particular host and profile. In this example, `AppNode01` and `AppNode02` are the application nodes.

### Q8. What is a Node Agent?

The Node Agent is a process on a federated application node. It communicates with the DMGR and supports management and synchronization of the node configuration.

### Q9. What is the difference between DMGR and Node Agent?

The DMGR centrally manages the cell. The Node Agent runs on each managed node and communicates with the DMGR to support node administration.

### Q10. What is the master configuration repository?

It is the authoritative cell configuration repository maintained by the DMGR. Managed nodes synchronize their local configuration from it.

### Q11. What is the default DMGR SOAP port?

A commonly used default is `8879`, but the actual port must be verified from the DMGR profile's `serverindex.xml`.

### Q12. What are the default DMGR Administrative Console ports?

Common defaults are HTTP `9060` and HTTPS `9043`. Actual values may differ if the profile ports were customized.

### Q13. Can we create multiple profiles from the same WebSphere installation?

Yes. Profiles share the product binaries but have separate runtime configurations, server definitions, logs and port assignments.

### Q14. What is the difference between a DMGR profile and a Cell profile?

A DMGR profile creates the management process. A Cell profile creates a DMGR profile and an application-server node profile together as a combined profile-creation operation.

### Q15. Why do we use a separate Custom profile on each application server?

Each host needs its own managed runtime environment. Separate Custom profiles allow the DMGR to manage application-server processes across different machines.

### Q16. What happens if the DMGR is down?

Existing application-server processes can generally continue serving requests, but centralized administration and configuration changes are unavailable until the DMGR is restored. The impact on a particular operation depends on the environment and the operation being performed.

### Q17. What happens if a Node Agent is down?

The application-server process may continue running, but the DMGR loses normal management and synchronization communication with that node until the Node Agent is restored.

### Q18. Can the DMGR and application servers run on separate machines?

Yes. This is a standard multi-machine Network Deployment topology.

### Q19. Why do we need a SOAP connection between the DMGR and managed nodes?

The SOAP connector is used by administration tools and node federation/management operations to communicate with the DMGR. The configured connector port must be allowed through the network firewall.

### Q20. What is the difference between installation and profile creation?

Installation places the WebSphere product binaries on the server. Profile creation establishes the runtime environment, such as a DMGR or Custom node, using those binaries.

### Q21. Where do you create a WebSphere cluster in this implementation?

From the DMGR Administrative Console: **Servers → Clusters → WebSphere application server clusters → New**. In this SOP the cluster name is `cluster`.

### Q22. Do you create cluster members on each application host separately?

No. In this implementation, both cluster members are created centrally through the DMGR cluster wizard. Assign `AppSrv01Member` to `AppNode01` and `AppSrv02Member` to `AppNode02`.

### Q23. Why select Generate unique HTTP ports when creating cluster members?

It helps assign distinct port values to the members so that they do not conflict. The generated values must still be reviewed against the approved port plan and firewall requirements.

### Q24. Does creating a cluster automatically deploy the application?

No. Cluster creation establishes the cluster and its members. The application must be installed separately and mapped to the cluster as the deployment target.

### Q25. Can application servers continue running if the DMGR becomes unavailable?

Generally, already-running application servers can continue processing requests. However, centralized administration, configuration changes and some management operations will be unavailable until the DMGR is restored.

## 20. End-to-end implementation checklist

Use this checklist during the build and handover.

- [ ] Confirm the supported Linux release and approved WAS version/fix-pack combination.
- [ ] Download Installation Manager, WAS ND, required SDK and fix-pack media.
- [ ] Transfer and verify offline repositories on all three servers.
- [ ] Complete OS, DNS, time, filesystem, resource-limit and firewall prerequisites.
- [ ] Create the approved WebSphere service account and directories.
- [ ] Install Installation Manager locally on all three servers.
- [ ] Install WAS ND binaries locally on all three servers.
- [ ] Verify product and Java SDK versions on all three servers.
- [ ] Create `Dmgr01` on Server 1.
- [ ] Start DMGR and record its actual SOAP and console ports.
- [ ] Create `AppSrv01` Custom profile on Server 2.
- [ ] Federate `AppNode01` to the DMGR.
- [ ] Create `AppSrv02` Custom profile on Server 3.
- [ ] Federate `AppNode02` to the DMGR.
- [ ] Start and verify both Node Agents.
- [ ] Confirm both nodes are available in the DMGR console.
- [ ] Create cluster `cluster` from the DMGR Administrative Console.
- [ ] Add `AppSrv01Member` on `AppNode01` through the cluster wizard.
- [ ] Add `AppSrv02Member` on `AppNode02` through the cluster wizard.
- [ ] Generate and review unique member ports.
- [ ] Save the DMGR configuration and synchronize nodes.
- [ ] Start the cluster and verify both members reach Started state.
- [ ] Deploy the application to cluster `cluster` using the DMGR console, if included in the build scope.
