# IBM WAS High CPU – Real Production Troubleshooting Walkthrough

Let's take a realistic IBM WebSphere Application Server (WAS) production incident and troubleshoot it as an application support engineer.

## Scenario

Production alert: Server CPU is 95%

| Metric          | Value                        |
| --------------- | ---------------------------- |
| Linux server    | wasprod01                    |
| Total CPU usage | 95%                          |
| WAS instances   | 3 JVMs                       |
| JVM 1           | 20% CPU                      |
| JVM 2           | 380% CPU                     |
| JVM 3           | 15% CPU                      |
| Impact          | Application response is slow |

Our goal is to find which JVM, which thread, and which Java code is causing the high CPU.

## Step 1 — Check server CPU

Connect to the Linux server and run:

```bash
top
```

Press `Shift + P` to sort by CPU.

Example:

```text
 PID     USER      %CPU    COMMAND
 24180   wasuser    380     java
 31872   wasuser     20     java
 40211   wasuser     15     java
  1034   root         2     java
```

### What do you understand from this?

* PID `24180` is consuming 380% CPU.
* This is likely the problematic WAS JVM.
* Other JVMs appear to have lower CPU usage.

We will investigate PID `24180`.

## Step 2 — Identify which WebSphere JVM this PID belongs to

Run:

```bash
ps -fp 24180
```

To see the full command line:

```bash
ps -ww -p 24180 -o args=
```

Example output:

```text
/opt/IBM/WebSphere/AppServer/java/bin/java
-Xmx4096m
-Xms2048m
-Dserver.name=OrderServer01
-Dwas.install.root=/opt/IBM/WebSphere/AppServer
```

Now you know that PID `24180` belongs to `OrderServer01`.

If multiple WAS JVMs are running, use the process command line, server configuration, or process listing to distinguish them.

## Step 3 — Find the high-CPU thread inside the JVM

Run:

```bash
top -H -p 24180
```

Press `Shift + P` to sort by CPU usage.

Example:

```text
PID      %CPU   COMMAND
24215   98.7    java
24218   85.2    java
24225   72.4    java
24230   40.5    java
```

These are Linux thread IDs (TIDs) inside JVM `24180`.

The highest-consuming thread is:

```text
TID = 24215
CPU = 98.7%
```

A single thread using close to 100% CPU generally means it is using one logical CPU core heavily.

## Step 4 — Convert the thread ID to hexadecimal

Linux shows thread IDs in decimal, but Java thread dumps often show native thread IDs in hexadecimal.

Run:

```bash
printf '%x\n' 24215
```

Output:

```text
5e67
```

### Thread mapping

| Item          | Value  |
| ------------- | ------ |
| JVM PID       | 24180  |
| Linux TID     | 24215  |
| Hex thread ID | 0x5e67 |
| CPU           | 98.7%  |

We will search for `5e67` in the thread dump.

## Step 5 — Take thread dumps during the CPU issue

First, confirm the process and the user:

```bash
ps -fp 24180
```

Take a dump:

```bash
kill -3 24180
```

This sends SIGQUIT to the JVM. In IBM Java, it typically generates a javacore in the configured dump directory.

Example dump files:

```text
javacore.20261128.134501.24180.0001.txt
javacore.20261128.134531.24180.0002.txt
javacore.20261128.134601.24180.0003.txt
```

Take 3 dumps, 30 seconds apart, while CPU is still high.

```bash
kill -3 24180
sleep 30
kill -3 24180
sleep 30
kill -3 24180
```

Before taking dumps, ensure sufficient disk space and check your JVM dump configuration. Javacores can contain sensitive application data, so protect them.

## Step 6 — Locate the javacore files

Check the current directory first:

```bash
ls -ltr javacore*
```

If you don't know where the dumps are generated:

```bash
find /opt/IBM/WebSphere -name "javacore.*.txt" -type f 2>/dev/null
```

You can also check the JVM dump configuration in the WAS server's settings or the JVM startup arguments to determine the configured dump directory.

## Step 7 — Search for the hot thread in the javacore

Our hot thread's hexadecimal ID was `5e67`.

Search for it:

```bash
grep -in "5e67" javacore.20261128.134501.24180.0001.txt
```

Or:

```bash
grep -in "0x5e67" javacore.20261128.134501.24180.0001.txt
```

Example thread information:

```text
3XMTHREADINFO      "WebContainer : 12"
3XMTHREADINFO1     (native thread ID: 0x5e67)
3XMTHREADINFO3     Java call stack:
```

This tells us the Linux hot thread maps to a Java WebContainer thread.

## Step 8 — Analyze the Java stack trace

Example javacore stack:

```text
3XMTHREADINFO      "WebContainer : 12"
3XMTHREADINFO1     (native thread ID: 0x5e67)
3XMTHREADINFO3     Java call stack:

4XESTACKTRACE
    at com.company.orders.OrderService.processOrders(OrderService.java:245)
    at com.company.orders.OrderServlet.doPost(OrderServlet.java:108)
    at javax.servlet.http.HttpServlet.service(HttpServlet.java:...)
    at com.ibm.ws.webcontainer.servlet.ServletWrapper.service(ServletWrapper.java:...)
    at com.ibm.ws.webcontainer.WebContainer.handleRequest(WebContainer.java:...)
```

### How to interpret it

| Stack method                 | Meaning                                    |
| ---------------------------- | ------------------------------------------ |
| OrderService.processOrders() | Business logic is executing                |
| OrderServlet.doPost()        | Request is coming through a servlet        |
| ServletWrapper.service()     | WAS WebContainer is processing the request |
| WebContainer.handleRequest() | WAS web request handling                   |

In this example, focus on:

```text
com.company.orders.OrderService.processOrders(OrderService.java:245)
```

The application developer should investigate line 245 of `OrderService.java`.

## Step 9 — Compare all 3 thread dumps

This is the most important step. One thread dump shows what the thread was doing at a moment in time. Comparing multiple dumps helps you determine whether it is continuously busy with the same work.

| Dump   | Hot thread | Stack                        |
| ------ | ---------- | ---------------------------- |
| Dump 1 | 0x5e67     | OrderService.processOrders() |
| Dump 2 | 0x5e67     | OrderService.processOrders() |
| Dump 3 | 0x5e67     | OrderService.processOrders() |

If the same thread is consuming high CPU and repeatedly appears in the same method or same execution path, it may be stuck in a CPU-intensive loop or repeatedly performing expensive processing.

### Example of a possible coding issue

```java
while (true) {
    if (orders.isEmpty()) {
        continue;
    }
}
```

If the loop has no effective wait or exit condition, it can consume CPU continuously.

Other common causes:

* Infinite loops
* Excessive iterations
* Complex JSON/XML parsing
* Regex processing on large input
* Large data processing in memory
* Repeated object creation
* Recursion
* Application retry loops
* Excessive concurrent requests

## Step 10 — Identify the root cause and next action

### Example incident conclusion

Affected JVM identified: OrderServer01 (PID 24180)

* CPU utilization: 380%
* Hot thread: `WebContainer : 12`
* Linux TID: `24215`
* Hex TID: `0x5e67`
* Stack: `OrderService.processOrders()`
* Repeated stack across dumps: Yes

**Next action:** Share the javacore evidence with the application team to investigate the processing loop or excessive computation in `OrderService.processOrders()`.

If production impact is severe, follow your incident procedure to mitigate traffic or restart the affected JVM if authorized. Capture evidence before restarting, because a restart may clear the opportunity to investigate the hot thread.

## Quick command cheat sheet

```bash
# 1. Identify high CPU processes
top

# 2. Find Java processes
ps -eo pid,%cpu,%mem,args --sort=-%cpu | grep java

# 3. Identify which WAS server is running under the PID
ps -ww -p 24180 -o args=

# 4. Find hot threads
top -H -p 24180

# 5. Convert TID decimal to hexadecimal
printf '%x\n' 24215

# 6. Take javacore
kill -3 24180

# 7. Find javacore
ls -ltr javacore*

# 8. Search hot thread in dump
grep -in "5e67" javacore*.txt
```

> **Production support tip:** Never conclude the root cause from CPU percentage alone. Always correlate Linux PID → TID → hexadecimal thread ID → Java stack → multiple dumps. This is the strongest evidence-based approach to identifying which JVM and which application code is causing high CPU in WAS.
