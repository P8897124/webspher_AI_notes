# IBM WebSphere ND – SSL/TLS Certificate Installation SOP

Production administration procedure | WebSphere ND 8.5.5 / 9.0 | Linux | GUI-based certificate management

This document provides an end-to-end operational procedure for installing, renewing, configuring and troubleshooting CA-signed SSL/TLS certificates on IBM WebSphere Application Server Network Deployment.

**Scope:** WebSphere ND application server certificate management using `NodeDefaultKeyStore` and `NodeDefaultTrustStore`.

F5, IHS and other infrastructure components are excluded.

## 2. SSL/TLS fundamentals

### 2.1 What is SSL/TLS?

SSL (Secure Sockets Layer) and TLS (Transport Layer Security) are cryptographic protocols used to secure communication between clients and servers.

TLS is the modern replacement for SSL. In production, use the TLS versions approved by your organization's security policy.

**Why do we need SSL/TLS?**

- Confidentiality – encrypts communication.
- Authentication – verifies server identity.
- Integrity – helps detect data modification.
- Secure communication – protects information exchanged between client and server.

### 2.2 How HTTPS communication works

1. **Client / Browser** requests an HTTPS connection (TLS handshake begins).
2. **WebSphere Application Server** presents its personal certificate.
3. **Certificate validation:** the client checks hostname, validity, signature and CA chain.
4. **Successful TLS handshake.**
5. **Encrypted communication begins.**

## 3. Certificate types and their purposes

| Certificate / File | Purpose |
| --- | --- |
| Personal certificate | Identifies the WebSphere server and is associated with its private key |
| Private key | Used in cryptographic operations to prove server identity; must remain protected |
| Public key | Shared as part of the certificate and used in public-key cryptography |
| Root CA certificate | Establishes trust in the root Certificate Authority |
| Intermediate CA certificate | Establishes the intermediate certificate chain |
| Signer certificate | Public certificate imported to establish trust |
| Self-signed certificate | Certificate signed by its own private key |
| CA-signed certificate | Certificate issued and signed by a trusted CA |
| CSR | Request containing the server identity and public key, submitted to the CA |
| PKCS12 file | Keystore container that can contain private keys and certificates |

### 3.1 Personal certificate

- Stored in `NodeDefaultKeyStore`.
- Contains the server's public certificate.
- Has an associated private key.
- Used when the WebSphere server presents its identity during TLS communication.

### 3.2 Root CA certificate

- Represents the root Certificate Authority.
- Used as a trust anchor.
- Usually self-signed.
- Imported into the appropriate truststore when not already trusted.

### 3.3 Intermediate CA certificate

- Issued by the root CA or another intermediate CA.
- Used to establish the certificate chain.
- Must be available to the certificate validation process.

### 3.4 Signer certificate

A signer certificate is a trusted public certificate stored in a truststore. It can be a root CA certificate, intermediate CA certificate or another trusted server certificate.

### 3.5 Self-signed vs CA-signed certificate

| Self-signed | CA-signed |
| --- | --- |
| Signed by its own private key | Signed by a Certificate Authority |
| Not automatically trusted by external clients | Can be trusted when the issuing CA chain is trusted |
| Often used for initial/default configurations and testing | Commonly used for production server identity |
| Trust must be established separately | Trust follows the CA trust chain |

## 4. WebSphere ND keystore and truststore architecture

WebSphere ND provides default keystores and truststores at different configuration scopes.

| Keystore / Truststore | Purpose |
| --- | --- |
| DmgrDefaultKeyStore | DMGR personal certificate |
| DmgrDefaultTrustStore | Trusted certificates used by DMGR |
| NodeDefaultKeyStore | Application node personal certificates |
| NodeDefaultTrustStore | Trusted certificates used by application node |
| CellDefaultKeyStore | Cell-scope personal certificates |
| CellDefaultTrustStore | Cell-scope trusted certificates |
| DmgrDefaultRootStore | DMGR root certificate keys |
| NodeDefaultRootStore | Node root certificate keys |

**Important distinction:**

- KeyStore stores personal identities and their associated private keys.
- TrustStore stores certificates trusted for validating peer identities.
- RootStore is used for root certificate management in WebSphere's default certificate hierarchy.

For this SOP, we will work with:

```
NodeDefaultKeyStore
NodeDefaultTrustStore
```

IBM documents the default keystore configuration and its PKCS12 files in its official documentation (see Section 26).

```

### 5.4 Default DMGR truststore location

```
<DMGR_PROFILE>/config/cells/<CELL_NAME>/nodes/<DMGR_NODE_NAME>/trust.p12

Assume:

```
WAS_HOME=/opt/IBM/WebSphere/AppServer
APP_PROFILE=/opt/IBM/WebSphere/AppServer/profiles/AppSrv01

                    ├── key.p12     (personal certificates and private keys)
                    └── trust.p12   (trusted certificates)
```

> **Note:** These are the typical default locations, not guaranteed paths for every installation. WebSphere supports custom keystore locations and remotely managed keystores. Always check the actual `Location` property in the Admin Console before running commands or taking backups.

### 5.6 Important WebSphere configuration files

| File | Purpose |
| --- | --- |
| `security.xml` | Contains SSL configuration and keystore references |
| `serverindex.xml` | Contains server endpoint and port information |
| `ssl.client.props` | Client-side SSL properties for WebSphere administrative clients |
| `key.p12` | Default personal keystore |
| `trust.p12` | Default truststore |
| `root-key.p12` | Root certificate keystore in applicable default configurations |

Typical security configuration location:

```
<WAS_PROFILE>/config/cells/<CELL_NAME>/security.xml
```

For a particular node:

```
<WAS_PROFILE>/config/cells/<CELL_NAME>/nodes/<NODE_NAME>/
```

`security.xml` is configuration metadata, not a certificate file. Do not manually edit it for normal certificate installation.

### 5.7 Certificate working directory

Create a separate working directory for certificate files.

```
mkdir -p /opt/IBM/certificates
mkdir -p /opt/IBM/certificates/backup
mkdir -p /opt/IBM/certificates/received
```

Recommended structure:

```
/opt/IBM/certificates/
       |
       |-- csr/
       |     |-- appnode01.csr
       |
       |-- received/
       |     |-- appnode01.cer
       |     |-- rootCA.cer
       |     |-- intermediateCA.cer
       |
       |-- backup/
             |-- key.p12
             |-- trust.p12
```

Protect this directory with appropriate OS permissions. The backup contains private-key material and must be restricted.

## 8. Generate CSR in WebSphere ND

**Main certificate installation procedure.**

### 8.1 Understand the CSR process

CSR stands for Certificate Signing Request.

When we generate a CSR in WebSphere:

1. WebSphere generates a public/private key pair.
2. The private key is stored in `NodeDefaultKeyStore`.
3. The public key is included in the CSR.
4. The CSR contains the requested server identity.
5. The CSR is digitally signed using the corresponding private key.
6. The CSR is submitted to the CA team.

The private key is never sent to the CA.

### 8.2 Example certificate information

Assume the following application server:

| Parameter | Value |
| --- | --- |
| Cell | ProductionCell |
| Node | AppNode01 |
| Server | AppServer01 |
| Keystore | NodeDefaultKeyStore |
| Certificate alias | appnode01_ssl |
| Hostname | appnode01.company.com |
| HTTPS port | 9443 |
| Country | IN |

### 8.3 Navigate to CSR creation

Login:

```
https://dmgr-hostname:9043/ibm/console
```

Navigate to:

```
Security
   |
   +-- SSL certificate and key management
          |
          +-- Key stores and certificates
```

Select the appropriate node scope and open:

```
NodeDefaultKeyStore
```

Select:

```
Personal certificate requests
       |
       +-- New
```

### 8.4 CSR fields to configure

| Field | Example | Requirement |
| --- | --- | --- |
| Certificate request file | `/opt/IBM/certificates/appnode01.csr` | Required |
| Key label | `appnode01_ssl` | Required |
| Common Name | `appnode01.company.com` | Required |
| Organization | `Company Pvt Ltd` | CA policy |
| Organizational Unit | `Middleware` | Optional / policy |
| Locality | `Hyderabad` | Optional / policy |
| State | `Telangana` | Optional / policy |
| Country | `IN` | CA policy |
| Key size | 2048 or 3072 | Security policy |
| Signature algorithm | SHA256 with RSA, if RSA | Security policy |
| SAN DNS | `appnode01.company.com` | Required for modern hostname validation |

For SAN, include every hostname that clients will use to access this server.

> **Important:** The exact CSR fields and SAN configuration depend on the WebSphere version, fix pack and CA requirements. If the console does not expose the required SAN extension, use an approved supported method to generate the CSR. Do not submit a CSR missing required SAN values.

### 8.5 Generate CSR

Click:

```
Apply
   |
   +-- Save
```

WebSphere creates the certificate request.

The file will be available at:

```
/opt/IBM/certificates/appnode01.csr
```

The private key remains in:

```
NodeDefaultKeyStore
```

### 8.6 Verify the CSR

Execute:

```
openssl req -in /opt/IBM/certificates/appnode01.csr -noout -text
```

Verify the following:

- Subject CN.
- Organization.
- Country.
- Public key algorithm.
- Public key size.
- Signature algorithm.
- SAN DNS values, if included.

Verify CSR signature:

```
openssl req -in /opt/IBM/certificates/appnode01.csr -noout -verify
```

Expected output:

```
Certificate request self-signature verify OK
```

This verifies the CSR's signature, not that the CA has issued or trusted the certificate.

## 9. Submit CSR to Certificate Authority team

Once the CSR is verified, raise a certificate request through your organization's approved CA process.

### 9.1 Files to submit

| File to submit | Required |
| --- | --- |
| `appnode01.csr` | Certificate Signing Request |

**Information to provide to CA:**

- Server FQDN.
- Environment: Production.
- Certificate purpose: WebSphere HTTPS.
- SAN DNS names.
- Certificate validity requirement.
- Certificate type: Server Authentication.

**Files never to submit (prohibited):**

- Private key.
- Complete `key.p12` keystore.
- Keystore password.

### 9.2 Example CA request

> Hi CA Team,
>
> Please find attached the CSR file for the IBM WebSphere ND application server.
>
> **Certificate Details:**
>
> - Server FQDN: appnode01.company.com
> - Environment: Production
> - Application: WebSphere Application Server ND
> - Certificate Purpose: HTTPS Server Authentication
> - Certificate Type: CA-signed SSL/TLS certificate
> - SAN DNS: appnode01.company.com
> - Requested Validity: As per company security policy
>
> Kindly process the CSR and provide the following:
>
> 1. CA-signed server certificate.
> 2. Intermediate CA certificate(s).
> 3. Root CA certificate.
> 4. Certificate chain, if available.
>
> Please provide the certificates in a WebSphere-compatible format.
>
> Regards,
> Middleware Administration Team

## 10. Receive certificates from the CA team

After processing, the CA team will return the signed certificate and CA chain.

Example:

```
appnode01.cer
intermediateCA.cer
rootCA.cer
```

The CA may instead supply a `.crt`, `.pem`, `.p7b` or `.p12` file depending on its certificate delivery process.

### 10.1 Understand each received file

| File | Issued by | Purpose |
| --- | --- | --- |
| `appnode01.cer` | CA | Signed application server certificate |
| `intermediateCA.cer` | CA | Intermediate trust chain |
| `rootCA.cer` | CA | Root trust anchor |

### 10.2 Verify received certificates

Check the server certificate:

```
openssl x509 -in appnode01.cer -noout -text
```

Check validity:

```
openssl x509 -in appnode01.cer -noout -dates
```

Check issuer and subject:

```
openssl x509 -in appnode01.cer -noout -subject -issuer
```

Check SAN:

```
openssl x509 -in appnode01.cer -noout -ext subjectAltName
```

Confirm the issued certificate corresponds to the public key in the original CSR:

```
openssl req -in appnode01.csr -pubkey -noout \
| openssl pkey -pubin -outform DER \
| openssl dgst -sha256
```

```
openssl x509 -in appnode01.cer -pubkey -noout \
| openssl pkey -pubin -outform DER \
| openssl dgst -sha256
```

The SHA-256 public-key fingerprints must match.

This is a useful check before receiving the certificate into WebSphere.

| --- | --- |

### 12.1 Verify installation

Navigate:

```
NodeDefaultKeyStore
    |
    +-- Personal certificates
```

You should see:

```
Alias: appnode01_ssl

Subject:
CN=appnode01.company.com

Issuer:
Company Intermediate CA
```

The certificate must be associated with the original private key.

If WebSphere reports that the certificate does not match the request, stop and investigate the CSR, alias and certificate public-key match. Do not generate a new key and attempt to receive the old certificate against it.

IBM's certificate-management procedures distinguish receiving the personal certificate from managing trusted signer certificates.

### 16.1 Verify from WebSphere Admin Console

Navigate:

```
Security
   |
   +-- SSL certificate and key management
          |
          +-- Key stores and certificates
                 |
                 +-- NodeDefaultKeyStore
                        |
                        +-- Personal certificates
```

Verify:

- Certificate alias.
- Subject.
- Issuer.
- Validity dates.
- Key size.
- SAN values.

### 16.2 Verify using OpenSSL

Execute from a system that can reach the application server:

```
openssl s_client \
-connect appnode01.company.com:9443 \
-servername appnode01.company.com \
-showcerts
```

To view the certificate:

```
openssl s_client \
-connect appnode01.company.com:9443 \
-servername appnode01.company.com \
</dev/null 2>/dev/null \
| openssl x509 -noout -subject -issuer -dates
```

Check the following:

- Correct certificate is presented.
- Hostname matches.
- Certificate is not expired.
- TLS handshake completes.
- Certificate chain validates.

For a full chain verification, use the appropriate CA bundle with OpenSSL's `-CAfile` option.

### 16.3 Verify using browser

Open:

```
https://appnode01.company.com:9443
```

Check the browser's certificate information.

Confirm:

- Issued to.
- Issued by.
- Valid from.
- Valid until.
- Subject Alternative Names.
- Certificate path.

## 17. Certificate renewal procedure

Certificate renewal follows almost the same process as new certificate installation.

| Step | Activity |
| --- | --- |
| 1 | Check certificate expiration |
| 2 | Identify existing certificate alias |
| 3 | Back up keystore and configuration |
| 4 | Generate new CSR |
| 5 | Submit CSR to CA |
| 6 | Receive new signed certificate |
| 7 | Import any missing CA signers |
| 8 | Receive new certificate against original CSR |
| 9 | Verify certificate and private key |
| 10 | Update SSL alias if necessary |
| 11 | Save and synchronize |
| 12 | Restart affected servers |
| 13 | Verify SSL handshake and application |

> **Production recommendation:** If the certificate renewal creates a new alias, update the SSL configuration to reference that alias. Do not delete the old certificate until the new certificate has been verified and the rollback window has passed.

---

## 18. Rollback procedure

If certificate installation fails:

1. Stop further changes.
2. Review the WebSphere logs.
3. Verify the certificate alias and SSL configuration.
4. If the new certificate cannot be used, restore the previous certificate alias.
5. If required, restore the backed-up keystore and truststore after ensuring that the affected server is stopped and the configuration is consistent.
6. Synchronize the node if configuration changes were made.
7. Restart the application server.
8. Verify HTTPS connectivity using the previous certificate.
9. Update the change ticket with the rollback result.

Do not overwrite keystore files while WebSphere is actively using them.

# Part 2 – SSL/TLS Troubleshooting and Interview Preparation

## 19. Important SSL/TLS troubleshooting scenarios

As a Middleware Administrator, you should be able to troubleshoot certificate-related production issues.

| Problem | Possible reason | Troubleshooting |
| --- | --- | --- |
| SSLHandshakeException | TLS handshake failure | Check protocol, cipher and certificate |
| PKIX path building failed | Missing CA trust | Verify root/intermediate signers |
| CertificateExpiredException | Certificate expired | Renew and install certificate |
| Hostname mismatch | Incorrect CN/SAN | Verify requested hostname against SAN |
| Certificate not found | Incorrect alias | Check personal certificate alias |
| Private key missing | Incorrect keystore or import | Verify original CSR and private key |
| Certificate chain incomplete | Missing intermediate certificate | Verify and complete chain |
| Node synchronization failure | Repository or connectivity issue | Check nodeagent logs |
| HTTPS connection refused | Server or port unavailable | Check application server status and port |
| TLS protocol mismatch | Unsupported protocol | Check SSL protocol configuration |
| No trusted certificate found | Missing signer certificate | Check relevant truststore |
| Wrong certificate presented | Incorrect SSL alias | Verify inbound SSL configuration |

# Part 3 – IBM WebSphere ND SSL/TLS Interview Questions and Answers

The following questions cover beginner, intermediate, advanced and L3 production troubleshooting topics.

## A. SSL/TLS fundamentals

**Q1. What is SSL/TLS?**

SSL/TLS is a security protocol used to encrypt communication between clients and servers. TLS is the modern version used for secure communication.

**Q2. What is HTTPS?**

HTTPS is HTTP communication secured using TLS.

**Q3. Why do we need SSL certificates?**

SSL certificates provide server identity authentication and enable secure encrypted communication.

**Q4. What is a digital certificate?**

A digital certificate is an electronic document containing identity information, public key, issuer, validity and digital signature.

**Q5. What is a Certificate Authority (CA)?**

A CA is a trusted organization that issues and signs digital certificates after validating certificate requests.

**Q6. What is the difference between SSL and TLS?**

SSL is the older protocol, while TLS is its successor with improved security. SSL versions are obsolete and should not be enabled in modern production environments.

**Q7. What are the three important security properties of TLS?**

- Confidentiality.
- Authentication.
- Integrity.

**Q8. What happens during a TLS handshake?**

The client and server negotiate the TLS version and cipher suite, authenticate the server certificate, establish shared cryptographic keys and start encrypted communication.

## B. Certificate types and CSR

**Q9. What is a personal certificate?**

A personal certificate identifies the WebSphere server and is associated with its private key. It is stored in the keystore.

**Q10. What is a signer certificate?**

A signer certificate is a trusted public certificate used to validate another certificate or certificate authority.

**Q11. What is a root CA certificate?**

It is the certificate of the top-level trusted Certificate Authority and acts as a trust anchor.

**Q12. What is an intermediate CA certificate?**

It is a certificate issued by the root CA or another intermediate CA and is used to sign lower-level certificates.

**Q13. What is a CSR?**

CSR stands for Certificate Signing Request. It contains the requested server identity and public key and is submitted to the CA for signing.

**Q14. What is present inside a CSR?**

- Subject Distinguished Name.
- Public key.
- Signature algorithm.
- CSR digital signature.
- Requested extensions, such as SAN, when included.

**Q15. Does a CSR contain the private key?**

No. It contains the public key and a digital signature created using the corresponding private key. The private key remains in the keystore.

**Q16. Which file do you send to the CA team?**

We send only the CSR file, for example `appnode01.csr`.

**Q17. Which files does the CA team provide?**

Usually the signed server certificate, intermediate CA certificate and root CA certificate.

**Q18. What is the purpose of CN?**

CN stands for Common Name. It identifies the server in the certificate's subject.

**Q19. What is SAN?**

SAN stands for Subject Alternative Name. It specifies DNS names or IP addresses covered by the certificate.

**Q20. Why is SAN important?**

Modern TLS hostname validation uses SAN. If the hostname is missing from SAN, clients may reject the certificate even when the CN matches.

**Q21. What is the difference between self-signed and CA-signed certificates?**

A self-signed certificate is signed by its own key, while a CA-signed certificate is signed by a trusted Certificate Authority.

**Q22. What is a certificate chain?**

A certificate chain links the server certificate to its intermediate CA certificates and ultimately to a trusted root CA.

**Q23. What is a certificate fingerprint?**

It is a cryptographic hash of a certificate used to identify and verify that certificate.

**Q24. What is certificate expiry?**

It is the date after which a certificate is no longer valid.

## C. WebSphere ND keystore and truststore

**Q25. What is a keystore in WebSphere?**

A keystore stores personal certificates and their corresponding private keys.

**Q26. What is a truststore in WebSphere?**

A truststore stores trusted certificates used to validate certificates presented by other systems.

**Q27. What is NodeDefaultKeyStore?**

It is the default node-level personal keystore used by WebSphere application server nodes.

**Q28. What is NodeDefaultTrustStore?**

It is the default node-level truststore used to validate peer certificates.

**Q29. What is CellDefaultKeyStore?**

It is the default cell-level keystore used for cell-scoped SSL identities.

**Q30. What is DmgrDefaultKeyStore?**

It is the default keystore containing the Deployment Manager's personal certificate.

**Q31. What is DmgrDefaultTrustStore?**

It is the default truststore used by the Deployment Manager.

**Q32. What is the difference between NodeDefaultKeyStore and NodeDefaultTrustStore?**

NodeDefaultKeyStore stores the node's identity and private key, whereas NodeDefaultTrustStore stores certificates trusted by that node.

**Q33. What is the default keystore format in WebSphere ND?**

The default file-based keystore type in current WebSphere ND configurations is PKCS12, generally using `.p12` files.

**Q34. Where is NodeDefaultKeyStore located?**

Typically:

```
<WAS_PROFILE>/config/cells/<CELL_NAME>/nodes/<NODE_NAME>/key.p12
```

**Q35. Where is NodeDefaultTrustStore located?**

Typically:

```
<WAS_PROFILE>/config/cells/<CELL_NAME>/nodes/<NODE_NAME>/trust.p12
```

**Q36. What is security.xml?**

It is a WebSphere configuration file containing security-related configuration, including SSL configuration and keystore references.

**Q37. What is the purpose of ssl.client.props?**

It contains SSL-related configuration properties used by WebSphere administrative and client processes.

**Q38. Can we directly modify key.p12 and trust.p12 using keytool?**

Technically, supported keystore tools can modify PKCS12 files, but in a managed WebSphere ND environment, use the Admin Console or supported IBM administration tools wherever possible. Direct modifications require careful configuration and synchronization management.

## D. SSL configuration and certificate installation

**Q39. How do you generate a CSR in WebSphere ND?**

Navigate:

```
Security
  → SSL certificate and key management
  → Key stores and certificates
  → NodeDefaultKeyStore
  → Personal certificate requests
  → New
```

Enter the required certificate information and generate the CSR.

**Q40. What fields are required while generating a CSR?**

The request file path, key label and Common Name are required by the standard console workflow. Other subject fields depend on CA policy. SAN should include the actual DNS names clients use.

**Q41. What is the purpose of a key label?**

It is an alias used to identify the certificate and corresponding private key in the keystore.

**Q42. What happens after submitting a CSR to the CA?**

The CA validates the request, signs the public key and provides the CA-signed server certificate and required chain certificates.

**Q43. How do you import a CA certificate in WebSphere?**

Navigate to the appropriate truststore, select Signer Certificates → Add, provide the certificate file and alias, then save the configuration.

**Q44. How do you install the signed server certificate?**

Navigate to the original personal certificate request and select Receive certificate from a certificate authority. Provide the signed certificate file and the appropriate data format.

**Q45. Why must we use the original CSR when receiving the signed certificate?**

Because the signed certificate must match the private key generated with that CSR.

**Q46. What is the purpose of SSL certificate alias configuration?**

It tells WebSphere which personal certificate to use for the applicable SSL endpoint.

**Q47. What is an SSL configuration in WebSphere?**

It defines the keystore, truststore, certificate aliases, TLS protocols, cipher suites and client authentication settings for an SSL endpoint.

**Q48. What is NodeDefaultSSLSettings?**

It is a default SSL configuration that can be used by node-level WebSphere endpoints.

**Q49. What is the difference between inbound and outbound SSL?**

- Inbound SSL: WebSphere acts as the TLS server and presents its server certificate.
- Outbound SSL: WebSphere acts as the TLS client and validates the remote server's certificate.

**Q50. What happens if we import a server certificate into the truststore instead of receiving it as a personal certificate?**

The truststore entry does not provide the server with its own private-key identity. The server certificate must be installed as a personal certificate associated with its original private key.

## E. Advanced SSL/TLS concepts

**Q51. What is one-way SSL?**

Only the server presents its certificate for authentication. The client validates the server's certificate.

**Q52. What is two-way SSL?**

Both client and server present certificates and authenticate each other. It is also called mutual TLS or mTLS.

**Q53. What is a cipher suite?**

A cipher suite defines the cryptographic algorithms used during a TLS connection, such as key exchange, authentication, encryption and integrity protection.

**Q54. What is TLS protocol negotiation?**

The client and server negotiate a mutually supported TLS version and cryptographic parameters during the handshake.

**Q55. What is PKCS12?**

PKCS12 is a standard container format that can store private keys and certificates, commonly using `.p12` or `.pfx`.

**Q56. What is the difference between `.cer` and `.p12`?**

A `.cer` generally contains a public certificate, whereas `.p12` can contain a private key and associated certificates.

**Q57. What is the difference between JKS and PKCS12?**

JKS is Java's traditional keystore format. PKCS12 is a standardized interoperable keystore container format.

**Q58. What is certificate pinning?**

Certificate pinning is a security technique where an application trusts a specific certificate or public key rather than relying solely on the general CA truststore.

**Q59. What is certificate revocation?**

It is the process of invalidating a certificate before its normal expiration date, often through CRL or OCSP mechanisms.

**Q60. What are CRL and OCSP?**

- CRL: Certificate Revocation List, a published list of revoked certificates.
- OCSP: Online Certificate Status Protocol, which provides certificate revocation status checks.

**Q61. What is a wildcard certificate?**

A wildcard certificate covers multiple subdomains at a particular DNS level, for example `*.company.com`, subject to its SAN and hostname matching rules.

**Q62. What is certificate renewal?**

Certificate renewal is the process of obtaining and installing a new certificate before the existing one expires.

## F. L3 production troubleshooting scenarios

**Q63. Your application server is throwing SSLHandshakeException. What will you check?**

I will check the certificate validity, hostname, certificate chain, truststore, SSL protocol, cipher suites and WebSphere logs.

**Q64. What does PKIX path building failed mean?**

It generally means the certificate validation process cannot build a trusted certificate chain. I will verify the required root and intermediate certificates in the applicable truststore and check chain validity.

**Q65. Your certificate is installed successfully, but the old certificate is still presented. What will you check?**

I will verify the inbound SSL configuration, server certificate alias, keystore scope, node synchronization and server restart.

**Q66. The CA has provided a certificate, but WebSphere says it does not match the request. What will you do?**

I will verify the CSR alias, certificate public key and original CSR. I will ask the CA to issue the certificate against the correct CSR if necessary.

**Q67. What will you do if the certificate expires in production?**

I will coordinate emergency renewal, generate or use an approved CSR, obtain the signed certificate, install it, verify the alias and perform the required restart under an approved change.

**Q68. What happens if the intermediate CA certificate is missing?**

The certificate chain may be incomplete, resulting in certificate validation failures. I will obtain and configure the required intermediate certificate.

**Q69. Your WebSphere node is not synchronizing after certificate installation. What will you check?**

I will check nodeagent and DMGR logs, node connectivity, synchronization status and whether the keystore/configuration changes were saved correctly.

**Q70. How do you troubleshoot a certificate hostname mismatch?**

I will compare the hostname used by the client with the certificate SAN entries. If it is missing, I will request a corrected certificate.

**Q71. What if the certificate is valid but the application cannot establish HTTPS?**

I will check the active server certificate alias, SSL configuration, truststore, TLS protocol, cipher compatibility and the application server's SSL port.

**Q72. How do you troubleshoot a TLS version mismatch?**

I will inspect the configured protocol on both sides and compare supported TLS versions. I will use an approved common TLS version rather than enabling obsolete protocols.

**Q73. What is your approach if the new certificate installation causes application downtime?**

I will review logs, restore the previous certificate alias or backed-up keystore if necessary, restart the affected server and validate connectivity. I will also document the failure and rollback.

**Q74. How do you verify whether a server is presenting the correct certificate?**

I will use:

```
openssl s_client \
-connect appnode01.company.com:9443 \
-servername appnode01.company.com \
-showcerts
```

Then inspect the subject, issuer, expiry and SAN.

**Q75. How do you check whether a private key matches a certificate?**

I compare the SHA-256 fingerprints of their public keys extracted from the original CSR and the signed certificate. They should match.

## 22. Practical interview scenario – Complete certificate renewal

**Important L3 scenario.**

**Interviewer:** You are supporting a production WebSphere ND environment with two application nodes. The SSL certificate is expiring in 15 days. Explain how you will renew it.

**Answer:**

I will first identify the existing certificate alias, keystore locations and SSL configuration.

Then I will:

1. Take backups of the keystores and configuration.
2. Generate a CSR for each node if separate node identities are used.
3. Verify the CSR hostname, SAN and key information.
4. Submit the CSR files to the CA team.
5. Receive the signed certificates and CA chain.
6. Import missing CA signers into the required truststores.
7. Receive each signed certificate against its original CSR.
8. Verify the personal certificates and private keys.
9. Update the SSL certificate aliases if required.
10. Save and synchronize the nodes.
11. Perform a rolling restart during the approved change window.
12. Verify SSL handshakes, application availability and logs.
13. Update the change ticket and certificate expiry records.

**Interviewer:** Why would you generate separate CSRs for two nodes?

**Answer:** If each node has its own hostname and personal certificate identity, separate CSRs maintain the correct hostname-to-private-key association. A shared certificate can be used only when the certificate SANs and private-key distribution are intentionally designed to support that architecture.

Once you can perform these activities independently, you will have a strong practical foundation for WebSphere ND SSL/TLS certificate administration and L3 production support.
