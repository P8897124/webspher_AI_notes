# **IBM WebSphere Application Server – Types of Profiles and Profile Creation**

In IBM WebSphere Application Server (WAS), a **Profile** is a runtime environment created inside a WebSphere installation. It contains the configuration files, server definitions, logs, security settings, and other resources required to run and administer WebSphere.

**Important:** Installing WebSphere binaries does not automatically create a profile. After installation, we create profiles based on the architecture and server requirements.

## **1. Types of WebSphere profiles**

In traditional IBM WebSphere Application Server Network Deployment (ND), the main profile types are:

### **1. Deployment Manager (DMGR) Profile**

Centralized administration

**Purpose:**

- Used to centrally manage multiple WebSphere Application Servers.
- Manages the entire cell environment.
- Controls nodes, clusters, application deployments and configurations.
- Provides the WebSphere Administrative Console.

**Example:**

If you have two application servers on separate Linux machines, you can manage both through one DMGR.

### **2. Application Server Profile**

Application hosting

**Purpose:**

- Used to run Java/J2EE applications.
- Supports application deployment.
- Can run independently in standalone mode.
- In an ND environment, it can be federated into a DMGR cell.

**Example:**

You create an Application Server profile named `AppSrv01` to host your enterprise applications.

### **3. Custom Profile**

Managed node

**Purpose:**

- Creates a WebSphere node without a fully configured application server.
- Used when you want to add a node to an existing DMGR cell.
- After profile creation, you federate it using `addNode`.
- The DMGR can then manage the node and create or configure application servers on it.

**Example:**

You have an existing DMGR on Server 1 and want to add Server 2. You create a Custom profile on Server 2 and federate it with the DMGR.

### **4. Secure Proxy Profile**

**Purpose:**

- Provides a proxy server for handling and forwarding client requests.
- Can be used in supported WebSphere ND architectures for proxy and routing requirements.
- Helps provide an additional entry point between clients and application servers.

**Note:** Secure Proxy is a separately supported profile capability; its availability depends on the WebSphere version and installed components.

### **5. Other management profiles**

WebSphere ND also supports additional management profiles:

| Profile              | Purpose                                                                               |
| -------------------- | ------------------------------------------------------------------------------------- |
| Administrative Agent | Manages multiple standalone application server profiles on the same machine.          |
| Job Manager          | Coordinates and schedules administrative jobs across multiple WebSphere environments. |
| Cell Profile         | Creates a cell configuration containing a DMGR and an application server node.        |

These are less commonly required in a standard production architecture.

**Quick comparison**

| Profile              | Runs applications?           | Managed by DMGR?                               |
| -------------------- | ---------------------------- | ---------------------------------------------- |
| Deployment Manager   | No, primarily administration | N/A                                            |
| Application Server   | Yes                          | Can be federated                               |
| Custom               | Not initially                | Yes, after federation                          |
| Secure Proxy         | No, acts as a proxy          | Supported through its management configuration |
| Administrative Agent | No, administration           | Manages standalone servers                     |
| Job Manager          | No, job coordination         | Coordinates administrative jobs                |

IBM documents these profile types for WAS ND 9.0.5. Availability depends on the installed WebSphere edition.&#x20;

## **2. How to create a WebSphere profile**

There are two methods:

1. **GUI method:** Profile Management Tool (PMT).
2. **Command-line method:** `manageprofiles.sh` (Linux) or `manageprofiles.bat` (Windows).

In real-time middleware administration, both methods are useful. PMT is convenient for initial setup, while CLI is useful for automation and repeatable installations.

## **3. Prerequisites before profile creation**

Before creating a profile, verify the following:

- WebSphere binaries are installed successfully.
- IBM Installation Manager installation is completed.
- Correct WebSphere version and fix pack are installed.
- Required OS users and permissions are configured.
- Sufficient disk space is available.
- Hostname and DNS resolution are working.
- Required ports are available.
- Java and WebSphere installation directories are accessible.

Example Linux installation directory:

```
/opt/IBM/WebSphere/AppServer
```

Profile directory:

```
/opt/IBM/WebSphere/AppServer/profiles
```

Profile templates:

```
/opt/IBM/WebSphere/AppServer/profileTemplates
```

## **5. Create profiles using CLI (Linux)**

This is particularly important for Middleware Administrators working on Linux production servers.

### **A. Create Deployment Manager profile**

Navigate to the WebSphere bin directory:

```
cd /opt/IBM/WebSphere/AppServer/bin
```

Execute:

```
./manageprofiles.sh -create \
-templatePath /opt/IBM/WebSphere/AppServer/profileTemplates/management \
-serverType DEPLOYMENT_MANAGER \
-profileName Dmgr01 \
-profilePath /opt/IBM/WebSphere/AppServer/profiles/Dmgr01 \
-cellName ProductionCell01 \
-nodeName DmgrNode01 \
-hostName dmgr01.example.com
```

If administrative security is required, configure the administrator credentials using the supported `manageprofiles` parameters.

### **B. Create Application Server profile**

```
./manageprofiles.sh -create \
-templatePath /opt/IBM/WebSphere/AppServer/profileTemplates/default \
-profileName AppSrv01 \
-profilePath /opt/IBM/WebSphere/AppServer/profiles/AppSrv01 \
-cellName ProductionCell01 \
-nodeName AppNode01 \
-hostName app01.example.com
```

### **C. Create Custom profile**

On the second application server machine:

```
./manageprofiles.sh -create \
-templatePath /opt/IBM/WebSphere/AppServer/profileTemplates/managed \
-profileName Custom01 \
-profilePath /opt/IBM/WebSphere/AppServer/profiles/Custom01 \
-nodeName AppNode02 \
-hostName app02.example.com \
-dmgrHost dmgr01.example.com \
-dmgrPort 8879
```

This creates a custom profile and attempts federation with the specified Deployment Manager. Ensure the DMGR is running and the required network connectivity and security credentials are available.

IBM reference: [manageprofiles command – WAS 9.0.5](https://www.ibm.com/docs/en/was-nd/9.0.5?topic=tools-manageprofiles-command\&utm_source=chatgpt.com).

## **6. How to start and stop profiles**

After successful profile creation, you need to start and stop the corresponding WebSphere processes.

**Start DMGR:**

```
cd /opt/IBM/WebSphere/AppServer/profiles/Dmgr01/bin

./startManager.sh
```

**Stop DMGR:**

```
./stopManager.sh
```

**Start Application Server:**

```
cd /opt/IBM/WebSphere/AppServer/profiles/AppSrv01/bin

./startServer.sh server1
```

**Stop Application Server:**

```
./stopServer.sh server1
```

**Check running processes:**

```
ps -ef | grep java
```

**Check profile list:**

```
cd /opt/IBM/WebSphere/AppServer/bin

./manageprofiles.sh -listProfiles
```

| Server         | Profile  | Components                  |
| -------------- | -------- | --------------------------- |
| Linux Server 1 | Dmgr01   | Deployment Manager          |
| Linux Server 2 | Custom01 | Node Agent + Cluster Member |
| Linux Server 3 | Custom02 | Node Agent + Cluster Member |

Architecture flow:

1. Administrator logs into the DMGR Administrative Console.
2. DMGR manages both application nodes.
3. Node Agents communicate with DMGR.
4. Applications are deployed to cluster members.
5. IBM HTTP Server (IHS) forwards incoming requests to application servers through the WebSphere plugin.
6. Load balancing distributes application requests between cluster members.

**Important:** In this architecture, you normally create a DMGR profile on Server 1 and Custom profiles on Servers 2 and 3. You then federate the custom nodes and create cluster members through the DMGR.

## **9. Important interview questions**

**Q1. What is a WebSphere profile?**

A profile is an independent runtime environment containing configuration files, logs, server definitions and other resources required to run WebSphere.

**Q2. What is the difference between DMGR and Custom profiles?**

DMGR centrally manages the WebSphere cell. A Custom profile creates a managed node that can be federated into the DMGR cell.

**Q3. Can we create multiple profiles on one machine?**

Yes. Multiple profiles can be created under one WebSphere installation, provided sufficient resources and unique port assignments are available.

**Q4. Can we deploy applications directly to a Custom profile?**

Not before it is configured and managed through the DMGR. After federation, application servers and cluster members can be created and managed centrally.

**Q5. What is federation?**

Federation is the process of adding an application server node to an existing Deployment Manager cell using the `addNode` command or the profile creation federation process.

**Q6. Which command lists all profiles?**

```
./manageprofiles.sh -listProfiles
```

**Q7. Where are profile templates located?**

```
/opt/IBM/WebSphere/AppServer/profileTemplates
```

**Q8. What happens if two profiles use the same port?**

Port conflicts can prevent servers from starting or cause communication failures. Each profile's ports should be planned and checked before starting the servers.

## **10. Recommended practical learning sequence**

For your WebSphere administration preparation, practise these activities in order:

- Install WebSphere ND 9.0.5.
- Create a DMGR profile using PMT.
- Create an Application Server profile.
- Create a Custom profile on another Linux server.
- Federate the Custom profile into DMGR.
- Start and stop DMGR and Node Agents.
- Create a cluster and cluster members.
- Deploy a sample EAR application.
- Configure IHS integration.
- Verify application access through the load balancer.

**My recommendation:** Learn profile creation, federation, node agent management and cluster creation together. These are connected activities in an actual WebSphere Network Deployment production environment.

You can refer to the official IBM documentation: [WAS 9.0.5 – Managing profiles](https://www.ibm.com/docs/en/was-nd/9.0.5?topic=systems-managing-profiles-by-using-graphical-user-interface\&utm_source=chatgpt.com).
