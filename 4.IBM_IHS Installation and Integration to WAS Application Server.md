## 1. Purpose and expected outcome

Install IBM HTTP Server on a new Linux host and integrate it with an **already-running** WebSphere Application Server Network Deployment cell. The existing DMGR, node agents, application servers and applications remain in place. No new DMGR, application-server profile or node agent is required on the IHS host.

At completion:

- Users can access approved applications through IHS on TCP 80 and/or 443.
- The WebSphere web-server plug-in routes requests to the existing WAS application server or cluster.
- The IHS host is represented in the WAS cell as an **unmanaged node** with a web-server definition.
- The DMGR can generate and, when remote administration is configured correctly, propagate `plugin-cfg.xml`.
- IHS administration can be performed through the WAS console for supported operations.
- Logging, validation, rollback and operational ownership are documented.

## 2. Scope and exclusions

### In scope

1. Discovery and compatibility checks.
2. OS, account, storage, DNS and firewall readiness.
3. Installation Manager, IHS, Web Server Plug-ins and WCT/PCT installation.
4. Plug-in configuration using PCT.
5. IHS Administration Server setup and authentication.
6. Client-facing HTTP and HTTPS configuration.
7. Existing DMGR integration through an unmanaged node and web-server definition.
8. Plug-in generation, propagation and backend TLS configuration.
9. Application validation, monitoring, troubleshooting and rollback.

### Out of scope

- Installing or rebuilding DMGR.
- Creating or federating application-server nodes.
- Creating new application servers or clusters.
- Application code changes and application deployment (except mapping an existing application to the web server).
- Load-balancer/F5 implementation beyond documenting the required traffic path.

## 3. Target architecture and request flow

```text
                         End users / API clients
                                  |
                         DNS: application FQDN
                                  |
                         F5 / Load Balancer
                       (if present in the design)
                                  |
                      TCP 80 / TCP 443 (client TLS)
                                  |
                 +--------------------------------+
                 | New IHS host: ihsserver01      |
                 | RHEL 8                         |
                 |                                |
                 | IBM HTTP Server                |
                 | WebSphere Web Server Plug-in   |
                 | GSKit / plugin-key.kdb         |
                 | IHS Admin Server :8008         |
                 +---------------+----------------+
                                 |
                      Plug-in routing using
                         plugin-cfg.xml
                                 |
                HTTP :9080 or HTTPS :9443 (examples)
                                 |
          +----------------------+----------------------+
          |                                             |
  +-------v---------+                           +-------v---------+
  | WAS Cluster     |                           | WAS Cluster     |
  | Member 1        |                           | Member 2        |
  | appserver01     |                           | appserver02     |
  +-------+---------+                           +-------+---------+
          |                                             |
          +----------------------+----------------------+
                                 |
                     Existing WAS ND cell
                                 |
                       DMGR + Node Agents
                    Admin Console / Repository

Management path:
DMGR/Admin Console ---> IHS Admin Server :8008
DMGR ---> WAS nodes / application servers (existing cell management)
```

### Request sequence

1. A user resolves the application FQDN to the load balancer or IHS VIP, as designed.
2. The load balancer forwards the request to IHS on the configured listener port.
3. IHS receives the request and passes applicable application traffic to the WebSphere plug-in.
4. The plug-in reads `plugin-cfg.xml`, matches the URI/context root and virtual host, and selects an eligible WAS transport.
5. The request reaches the selected WAS cluster member over HTTP or HTTPS.
6. WAS processes the request and returns the response through the plug-in and IHS to the client.

**Important:** Client-to-IHS TLS and IHS-to-WAS TLS are separate connections. Enabling HTTPS on IHS does not automatically encrypt the backend connection.

## 5. Pre-change planning and discovery

### 5.1 Collect existing WAS details

On the DMGR host, use the correct WAS installation path and profile name:

```bash
cd "$WAS_HOME/bin"
./versionInfo.sh
./versionInfo.sh -maintenancePackages
```

If available, inspect Installation Manager inventory:

```bash
/opt/IBM/InstallationManager/eclipse/tools/imcl \
  listInstalledPackages -installationDirectory "$WAS_HOME"
```

Record and attach to the change ticket:

- WAS version, fix pack, interim fixes and build level.
- Java SDK level and GSKit/security maintenance level where applicable.
- DMGR host, profile, cell and SOAP connector port.
- Existing node names, cluster names and application-server member names.
- Application context roots and virtual hosts.
- Backend HTTP/HTTPS transport ports for each target cluster member.
- Current application health and baseline response time.
- Existing plug-in/web-server definitions, if any, to avoid duplicate names.

### 5.2 Confirm application mapping design

Decide with the application and security teams whether:

- All eligible existing applications should be mapped to this web server (`ALL`), or
- Only selected applications should be mapped (`None` initially, followed by explicit mapping).

For a production cell with multiple security domains, start with `None` and map only approved applications. IBM documents a possible KDB creation issue when `ALL` is selected across different security domains during web-server creation.

### 5.3 DNS and network readiness

Confirm forward and reverse DNS as required by enterprise standards:

```bash
hostname -f
getent hosts "$IHS_HOST"
getent hosts "$DMGR_HOST"
```

Confirm routes and connectivity from the correct source hosts. Examples (replace ports):

```bash
nc -vz "$DMGR_HOST" 8879
nc -vz "$DMGR_HOST" 9043
nc -vz <WAS_MEMBER_HOST> 9080
nc -vz <WAS_MEMBER_HOST> 9443
```

### 5.4 Firewall matrix

Open only the flows required by the approved topology. Port values below are examples, not universal defaults.

| Source | Destination | Port | Purpose |
|---|---|---:|---|
| Client / F5 | IHS | 80/tcp | HTTP listener, redirect or permitted HTTP service |
| Client / F5 | IHS | 443/tcp | HTTPS listener |
| DMGR host | IHS | 8008/tcp | IHS Administration Server (HTTP by default; secure it if required) |
| IHS host | WAS cluster members | 9080/tcp | Example backend HTTP transport |
| IHS host | WAS cluster members | 9443/tcp | Example backend HTTPS transport |
| Admin workstation | DMGR | 9043/tcp | Example Admin Console HTTPS port |
| Admin workstation / wsadmin host | DMGR | 8879/tcp | Example SOAP connector port |
| IHS host | DNS/NTP/enterprise services | As approved | Name resolution, time sync, logging/monitoring, certificate services |

Do not open every WAS port by default. Confirm actual listener ports from the WAS configuration and network/security teams. If the IHS Admin Server is configured for HTTPS, document and allow the corresponding secure admin port/protocol instead of assuming HTTP.

## 7. Prepare the IHS host and accounts

Use the enterprise-standard service account if one already exists. Example only:


## 10. Configure the IHS Administration Server

The IHS Administration Server is what allows the WAS Admin Console to perform supported remote IHS operations on an unmanaged node. It is not the same as the IHS client-facing HTTPS listener.

### 10.1 Run setupadm

On the IHS host, use the supported administrative procedure and run:

```bash
cd /opt/IBM/HTTPServer/bin
./setupadm
```

Follow the prompts for:

- Administration user ID.
- Administration group.
- IHS configuration/authentication directory (normally the IHS configuration directory).
- Files/directories for which the setup script should establish group access.

The setup utility adjusts ownership/group permissions for the administration server to access configuration and authentication files. Review the changes and ensure the targeted plug-in configuration directory/file is also accessible to the administration mechanism as required. Do not use broad `chmod 777` permissions.

### 10.2 Create the IHS Admin Server authentication credential

The Admin Server uses HTTP basic authentication credentials stored in `conf/admin.passwd`. Create the user ID that will also be entered in the WAS web-server definition:

```bash
cd /opt/IBM/HTTPServer/bin
./htpasswd -cm /opt/IBM/HTTPServer/conf/admin.passwd ihsadmin
```

Enter the password interactively. Do not place production passwords in shell history, scripts or tickets. Use `-c` only when creating the file initially; for later users, do not recreate/truncate the file—use the documented update form without `-c`.

### 10.3 Start and verify the Admin Server

```bash
cd /opt/IBM/HTTPServer/bin
./adminctl start
```

Verify process and listener (port is configurable; 8008 is the common default):

```bash
ps -ef | grep -i '[a]dmin'
ss -lntp | grep 8008
```

The admin server port and protocol must match the values entered later in the WAS console. If HTTPS is selected for administration, configure its certificate/trust first and use the HTTPS option in the web-server definition. Do not confuse this channel with application HTTPS on port 443.

**Privilege note:** IBM documents that the administration server may need to invoke `adminctl restart` with root privileges to perform successful IHS restarts. Implement only the narrowly scoped, IBM-supported privilege arrangement approved by the Linux/security teams. Do not grant unrestricted sudo access.

## 11. Configure client-facing HTTP and HTTPS on IHS

### 11.1 Back up the current configuration

```bash
cp -p /opt/IBM/HTTPServer/conf/httpd.conf \
  /opt/IBM/HTTPServer/conf/httpd.conf.pre_integration.$(date +%Y%m%d_%H%M%S)
```

### 11.2 Configure HTTP listener

Review `httpd.conf` and ensure there is one intended listener for port 80:

```apache
Listen 80
```

Do not add duplicate `Listen` directives. Confirm that the plug-in module and `WebSpherePluginConfig` directive created by PCT are present.

### 11.3 Create or import the IHS server certificate

Obtain the approved server certificate and full issuer chain from the enterprise CA. The certificate must match the public application FQDN (or approved SANs), be within its validity period, and include the correct private key.

Create a protected SSL directory:

```bash
mkdir -p /opt/IBM/HTTPServer/conf/ssl
chown -R root:ihsgrp /opt/IBM/HTTPServer/conf/ssl
chmod 750 /opt/IBM/HTTPServer/conf/ssl
```

Create a CMS key database using the GSKit command supplied with the installation. Confirm the exact executable name in the installed IHS/GSKit package; the following is an example:

```bash
cd /opt/IBM/HTTPServer/bin
./gskcapicmd_64 -keydb -create \
  -db /opt/IBM/HTTPServer/conf/ssl/ihs.kdb \
  -pw '<ENTER_SECURE_PASSWORD_INTERACTIVELY_OR_USE_APPROVED_SECRET_METHOD>' \
  -type cms -stash
```

Prefer an approved secret-handling method; do not leave literal passwords in shell history. Generate a CSR from the KDB, submit it to the CA, receive the signed personal certificate and complete chain, then import the signer/intermediate certificates and receive the signed personal certificate using the correct GSKit labels. The precise import commands depend on the CA files and labels supplied by your PKI team.

List certificates and confirm the personal certificate label:

```bash
./gskcapicmd_64 -cert -list \
  -db /opt/IBM/HTTPServer/conf/ssl/ihs.kdb -stashed
```

Record certificate expiry and renewal owner. Protect `.kdb` and `.sth` files; the stash file is sensitive.

### 11.4 Configure SSL in httpd.conf

Use the SSL module and directives supported by the installed IHS level. PCT or the installed IHS configuration may already have a module line; avoid duplicates. Example structure:

```apache
LoadModule ibm_ssl_module modules/mod_ibm_ssl.so
Listen 443

KeyFile /opt/IBM/HTTPServer/conf/ssl/ihs.kdb

<VirtualHost *:443>
    ServerName app.example.com:443
    SSLEnable
    SSLServerCert ihs-cert
</VirtualHost>
```

Replace `app.example.com` and `ihs-cert` with the actual FQDN and GSKit personal-certificate label. Confirm the module path and directives against the installed IHS documentation. If using multiple HTTPS virtual hosts/certificates, configure SNI and certificate selection according to the exact IHS release and enterprise design.

### 11.5 Decide HTTP policy

Choose one approved policy:

- **Dual protocol:** HTTP and HTTPS both serve application traffic, only when required.
- **Redirect:** HTTP redirects to HTTPS; HTTPS serves application traffic.

For a redirect, use a carefully scoped virtual-host or rewrite rule. Test F5 health probes, application callbacks, API clients, context roots and monitoring before enabling a global redirect. Do not accidentally redirect health-check paths or break applications that legitimately require HTTP.

### 11.6 Validate syntax and permissions

```bash
/opt/IBM/HTTPServer/bin/apachectl -t
```

Expected: `Syntax OK`.

Also verify that the IHS runtime account can read the certificate database and stash file, while unauthorized users cannot read them.

This is the key integration step. Do not install a WAS node agent on the IHS host for this topology. The IHS host is represented by an **unmanaged node** in the WAS cell.

On the DMGR host:

```bash
cd "$WAS_HOME/profiles/$DMGR_PROFILE/bin"
./serverStatus.sh dmgr
```

Confirm the DMGR is `STARTED`. Also check the relevant node agents and target application-server cluster members:

```bash
./serverStatus.sh nodeagent
```

Run the status command for the actual profile/server names in the environment. Confirm the Admin Console is reachable and the master repository is healthy before making changes.

### 12.2 Log in to the WAS Admin Console

Example URL (confirm the actual console port):

```text
https://wasdmgr01.example.com:9043/ibm/console
```

Use an authorized administrator account and verify that you are connected to the correct cell.

### 12.3 Create an unmanaged node

Navigate:

```text

  → Nodes
    → Add Node
```

| Field | Example |
|---|---|

Click **Finish**, then save the master configuration. Confirm the node appears in the Nodes collection.

**Why unmanaged node?** There is no WAS installation or node agent on the IHS machine. The IHS Administration Server provides the supported remote administration channel for IBM HTTP Server operations.

### 12.4 Create the web-server definition

Navigate:

```text

  → Server Types
    → Web servers
      → New
```

Select the new unmanaged node and provide:

| Field | Example / instruction |
|---|---|
| Web server name | `webserver1` (must be unique in the cell) |
| Web server type | IBM HTTP Server |
| Host name | `ihsserver01.example.com` |

Navigate to **Servers → Server Types → Web servers** and confirm `webserver1` is listed under the intended unmanaged node. Open its properties and recheck host, port, installation path, plug-in path and administration server details.

## 13. Generate and propagate the authoritative plug-in configuration

### 13.1 Generate `plugin-cfg.xml`

In the WAS Admin Console:

```text
Servers
  → Server Types
    → Web servers
      → select webserver1
        → Generate Plug-in
```

Wait for successful completion. The generated file reflects the WAS cell configuration, including eligible application mappings, URI groups/context roots, virtual host aliases, cluster members, backend transport ports and routing information.

### 13.2 Propagate the plug-in configuration

From the same web-server collection, select **Propagate Plug-in**. This uses the IHS Administration Server connection for a remote IBM HTTP Server when correctly configured.

Expected IHS-side file:

```text
/opt/IBM/WebPlugins/config/webserver1/plugin-cfg.xml
```

Verify on the IHS host:

```bash
ls -l /opt/IBM/WebPlugins/config/webserver1/plugin-cfg.xml
stat /opt/IBM/WebPlugins/config/webserver1/plugin-cfg.xml
```

Confirm the file timestamp reflects the latest generation and the IHS runtime account can read it. Do not manually edit this generated file; adjust WAS web-server/plug-in properties and regenerate instead.

### 13.3 If automatic propagation fails

1. Confirm `adminctl` is running and listening on the configured port.
2. Confirm DMGR-to-IHS firewall connectivity.
3. Confirm the host and port in the WAS web-server definition match IHS.
4. Confirm admin user ID/password match `conf/admin.passwd`.
5. Confirm HTTP versus HTTPS administration protocol matches on both sides.
6. Confirm IHS admin-server permissions cover the target plug-in configuration directory/file.
7. Review IHS `admin_error.log` / administration logs and WAS `SystemOut.log`, `SystemErr.log` and `trace.log` where relevant.
8. If approved, use a controlled manual file transfer from the correct DMGR-generated web-server definition path to the IHS plug-in path. Preserve ownership and read permissions, verify checksum, and record the manual propagation in the change ticket.

For manual transfer, first identify the authoritative file in the active DMGR profile repository; do not guess the node/cell directory. Copy it to `/opt/IBM/WebPlugins/config/webserver1/plugin-cfg.xml` and ensure the IHS process can read it. A common read permission is `0644`, but ownership/group must follow the enterprise security model.

### 13.4 Validate plug-in contents

```bash
grep -E 'ServerCluster|Transport|VirtualHostGroup|UriGroup' \
  /opt/IBM/WebPlugins/config/webserver1/plugin-cfg.xml
```

Confirm the expected application context root, virtual host alias, cluster and all intended member host/port combinations are present. Check that no unintended application is exposed through the web server.

## 14. Backend HTTPS: IHS plug-in to WAS (optional, security-driven)

This is a separate TLS connection from browser-to-IHS HTTPS.

```text
Client --HTTPS:443--> IHS --HTTPS:9443--> WAS cluster member
```

If the backend transport is HTTP, traffic between IHS and WAS is not encrypted. If the security policy requires encryption, configure HTTPS transports on the WAS application servers and configure the plug-in to trust the certificate chain presented by those WAS endpoints.

### 14.1 Confirm WAS HTTPS transport

In the WAS Admin Console, inspect the target server/cluster transport settings and identify the actual HTTPS transport port. Confirm the endpoint is listening and reachable from the IHS host:

```bash
nc -vz <WAS_MEMBER_HOST> <WAS_HTTPS_PORT>
```

Do not assume `9443`; use the configured port.

### 14.2 Configure plug-in trust store

The WAS web-server definition normally has a plug-in key database (`plugin-key.kdb`) and associated stash file. From the DMGR Admin Console:

```text
Servers
  → Server Types
    → Web servers
      → webserver1
        → Plug-in properties
          → Manage keys and certificates
```

Review the plug-in KDB. Add the CA signer/intermediate certificate(s) that issued the WAS application-server HTTPS certificate if they are not already trusted. For a certificate issued by the cell's default signer, verify that the correct signer is already present. For certificates issued by a separate enterprise CA, import the appropriate CA chain as signer certificates.

Save the configuration and use **Copy to web server key store directory** when available for the remote web server. The expected remote location is generally under:

```text
/opt/IBM/WebPlugins/config/webserver1/plugin-key.kdb
/opt/IBM/WebPlugins/config/webserver1/plugin-key.sth
```

Confirm the actual path shown in the WAS plug-in properties and in the generated plug-in configuration. Ensure the `.kdb` and `.sth` files are protected and readable by the plug-in runtime account. Do not email or expose these files.

### 14.3 Confirm generated transport protocol

After configuring the web-server definition and application-server transport selection, regenerate and propagate the plug-in configuration. Inspect the relevant `<Transport>` entries in `plugin-cfg.xml`. For encrypted backend connections, the selected member transport must use HTTPS and the correct port. Do not manually change generated XML as a substitute for configuring the WAS transport/plug-in properties.

### 14.4 Restart and test backend TLS

After KDB/trust changes and propagation, perform a controlled IHS restart/reload as required by the installed level and change plan. Test the application and inspect `http_plugin.log` for GSKit/certificate errors. Common causes include missing CA signer, expired certificate, hostname mismatch, unsupported protocol/cipher overlap, incorrect KDB path, missing stash file or file permission errors.

**Do not use an insecure plug-in setting or disable WAS HTTPS as a quick fix in production.** That changes the security posture and should only be considered under a separately approved risk decision.

## 15. Start services and perform end-to-end validation

### 15.1 Start order

For a first implementation, confirm the existing WAS application servers/cluster are already healthy. Then:

1. Start the IHS Administration Server if it is not running:
   ```bash
   /opt/IBM/HTTPServer/bin/adminctl start
   ```
2. Start IHS using the approved service account/privileged start mechanism:
   ```bash
   /opt/IBM/HTTPServer/bin/apachectl start
   ```
3. Verify listeners:
   ```bash
   ss -lntp | grep -E ':80|:443|:8008'
   ```

Do not blindly restart the existing DMGR or application servers for an IHS-only change.

### 15.2 Local IHS tests

```bash
/opt/IBM/HTTPServer/bin/apachectl -t
curl -I http://127.0.0.1/
curl -kI https://127.0.0.1/
```

`-k` is useful only for a temporary diagnostic that ignores certificate validation; it is not an acceptance test. Final HTTPS validation must verify the certificate chain and hostname.

### 15.3 Backend direct test

From the IHS host, test the exact WAS transport endpoints:

```bash
curl -I http://<WAS_MEMBER_HOST>:<WAS_HTTP_PORT>/<APP_CONTEXT_ROOT>
curl -I https://<WAS_MEMBER_HOST>:<WAS_HTTPS_PORT>/<APP_CONTEXT_ROOT>
```

For HTTPS, use normal certificate verification and the enterprise CA trust configuration. A temporary `-k` test may help isolate connectivity from trust, but it does not prove TLS is correctly configured.

### 15.4 Plug-in routed application test

Use the real application URL through the IHS hostname/VIP:

```bash
curl -I http://app.example.com/<APP_CONTEXT_ROOT>
curl -I https://app.example.com/<APP_CONTEXT_ROOT>
```

Test from an approved client network, not only localhost. Confirm:

- DNS resolves to the expected VIP/IHS address.
- F5 health check succeeds if a load balancer is present.
- Correct certificate and hostname are presented on HTTPS.
- Application context root returns the expected response.
- Authentication/SSO and session behavior work.
- Static content, redirects, cookies and large uploads work where applicable.
- Requests are routed to the expected cluster and fail over when one member is intentionally removed under an approved test.
- No unexpected direct backend exposure exists.

### 15.5 Verify logs

IHS access/error logs (common defaults):

```text
/opt/IBM/HTTPServer/logs/access_log
/opt/IBM/HTTPServer/logs/error_log
```

Plug-in log (common default):

```text
/opt/IBM/WebPlugins/logs/webserver1/http_plugin.log
```

Administration logs: inspect the IHS Admin Server log files under the configured IHS log/config locations (commonly `admin_error.log` and related files; exact names/paths depend on the installation).

Tail logs during a test:

```bash
tail -f /opt/IBM/HTTPServer/logs/error_log
 tail -f /opt/IBM/WebPlugins/logs/webserver1/http_plugin.log
```

Confirm log level is appropriate for production. Avoid verbose trace/debug logging indefinitely; enable it only for a controlled troubleshooting window and disable it afterward.

### 15.6 Acceptance evidence

- [ ] IHS and plug-in package inventory captured.
- [ ] IHS config syntax test passed.
- [ ] IHS Admin Server is running and reachable from DMGR.
- [ ] WAS unmanaged node and web-server definition exist in the correct cell.
- [ ] Plug-in generation and propagation completed.
- [ ] Plug-in XML contains expected app, virtual host, cluster and transports.
- [ ] `plugin-key.kdb`/stash file are present if backend TLS is used.
- [ ] HTTP policy and HTTPS certificate validated.
- [ ] Application URL succeeds through IHS.
- [ ] Logs show no unresolved plug-in, SSL or routing errors.
- [ ] Application owner and operations team sign off.

## 16. Post-implementation operations

### 16.1 When to regenerate and propagate plug-in configuration

Regenerate/propagate after changes that affect web-server routing, such as:

- Deploying or uninstalling an application mapped to this web server.
- Changing application context roots or virtual host mappings.
- Adding/removing cluster members or changing backend transport ports.
- Changing plug-in properties or routing behavior.

Use the WAS Admin Console and verify the generated file timestamp/content on IHS. Do not hand-edit `plugin-cfg.xml` for routine changes.

### 16.2 Routine health checks

Daily/shift checks should cover:

- IHS process and listener health.
- IHS Admin Server health if console-based administration is used.
- HTTP/HTTPS endpoint response.
- Plug-in log for repeated connection, SSL or routing errors.
- IHS error/access log growth and disk utilization.
- WAS cluster member health and backend connectivity.
- Certificate expiry monitoring and time synchronization.

### 16.3 Log rotation and retention

Configure log rotation using the enterprise Linux standard. Ensure IHS can reopen log files after rotation (use the documented IHS restart/reopen method for the installed release). Define retention, compression, forwarding to centralized logging and disk alerts. Do not delete active logs manually during production.

### 16.4 Certificate renewal

Track both:

1. Client-facing IHS certificate in the IHS KDB.
2. Backend WAS certificate trust chain in the plug-in KDB (when backend TLS is enabled).

For renewal, obtain the replacement certificate/chain, import it using the approved GSKit/WAS console process, verify labels and validity, propagate the plug-in KDB if changed, perform a controlled restart/reload and validate from a client and the IHS host. Keep the previous known-good KDB/config backup until acceptance.

### 16.5 Patch and fix-pack management

Before applying IHS, plug-in, GSKit or Installation Manager updates:

- Verify compatibility with the existing WAS maintenance level and RHEL release.
- Review IBM APARs/security bulletins and release notes.
- Back up IHS config, KDB/stash files, plug-in config and installation inventory.
- Test in non-production first.
- Apply through Installation Manager using the approved repository and rollback procedure.
- Re-run syntax, TLS, routing and application tests.

## 17. Troubleshooting guide

| Symptom | Likely checks | Corrective direction |
|---|---|---|
| IHS does not start | `error_log`, `httpd.conf` syntax, port conflict, ownership, module path, certificate KDB access | Run `apachectl -t`; resolve the first configuration error; check `ss -lntp`; correct permissions/module path |
| Port 80/443 not listening | Listener directive, firewall, process user, port already in use | Confirm `Listen`; check `ss`; check firewalld/network ACL; use approved privileged bind/start method |
| IHS Admin Server unavailable | `adminctl` process, admin port, firewall, `admin.passwd`, admin server protocol | Verify `adminctl start`, listener, credentials and exact port/protocol in WAS definition |
| WAS console cannot connect to IHS Admin Server | Host/port mismatch, credentials, HTTP/HTTPS mismatch, firewall, permissions, admin logs | Compare WAS web-server definition to IHS `admin.conf`; test DMGR-to-IHS port; validate `htpasswd` user; review admin logs |
| Plug-in propagation fails | Admin Server down, invalid credentials, permission issue on plug-in directory, network block | Fix admin channel and file access; retry propagation; use documented manual transfer only if necessary |
| HTTP 404 through IHS, direct WAS URL works | Application not mapped, wrong context root, virtual host alias missing, stale plug-in XML | Verify app mapping, host alias and generated `plugin-cfg.xml`; regenerate and propagate |
| HTTP 500 / 503 through IHS | Backend server down, wrong port, plug-in routing, application error | Review `http_plugin.log`, WAS `SystemOut.log`, cluster member state and backend reachability |
| Plug-in reports no route / URI mismatch | Context root or virtual host mismatch; wrong web-server mapping | Confirm URL, URI group, virtual host alias and application mapping; regenerate XML |
| Backend connection timeout/refused | Firewall, wrong host/port, WAS transport not listening, route issue | Test from IHS using `nc`; verify WAS transport and network ACL |
| Backend HTTPS handshake failure | Missing signer, expired/mismatched cert, wrong KDB/stash path, TLS/cipher mismatch | Verify plug-in KDB trust, certificate chain, generated HTTPS transport, file permissions and TLS compatibility |
| IHS HTTPS certificate warning | Wrong certificate label, missing intermediate, expired cert, FQDN/SAN mismatch | Inspect IHS KDB labels and chain; install correct full chain; verify DNS name and expiry |
| Works on one cluster member only | Member-specific port, certificate, firewall or application health | Compare each member's transport and logs; correct inconsistent member configuration |
| Changes not reflected after deployment | Plug-in XML not regenerated/propagated, wrong file path, stale file | Check timestamp and `WebSpherePluginConfig` path; regenerate and propagate; restart only if required |
| High latency | Backend response time, plug-in queue/connection settings, IHS resource saturation, network | Correlate IHS access log, plug-in log, WAS PMI/ThreadPool/DB metrics and network latency before tuning |

## 18. Rollback procedure

Rollback must be approved in the change record. The rollback objective is to remove the new IHS route from service and restore the previous application access path without changing the existing WAS application deployment.

### 18.1 Before implementation, preserve

- Original IHS `httpd.conf` and any included configuration files.
- IHS KDB and stash files (securely stored).
- Plug-in `plugin-cfg.xml`, `plugin-key.kdb` and stash file.
- Installation Manager package inventory and install logs.
- Existing DMGR configuration backup per enterprise policy.
- DNS/F5 pool/member and firewall change details.

### 18.2 Rollback execution

1. Drain/disable the new IHS member from F5 or remove the new DNS route according to the approved plan.
2. Confirm users can still reach the application through the previous supported route.
3. Stop IHS gracefully:
   ```bash
   /opt/IBM/HTTPServer/bin/apachectl stop
   ```
4. Stop the IHS Administration Server if required:
   ```bash
   /opt/IBM/HTTPServer/bin/adminctl stop
   ```
5. Restore the pre-change `httpd.conf`, included files and known-good KDB files if the issue is configuration-related.
6. If the web-server definition must be removed, use the WAS Admin Console to remove only the new `webserver1` definition and its dedicated unmanaged node after confirming no other object depends on them. Save the master configuration. Do not remove existing WAS nodes, clusters, applications or profiles.
7. Revert only the firewall/DNS/F5 changes introduced by this change.
8. Validate the previous application access path and obtain application-owner sign-off.
9. Retain logs and evidence for root-cause analysis. Uninstall IHS packages only if explicitly included in the rollback decision; do not uninstall shared Installation Manager components or unrelated IBM packages.

## 20. Interview questions and answers — Lead Middleware Administrator

Answers are intentionally concise but should be expanded with a real project example during an interview.

### Architecture and integration

**1. Explain the end-to-end request flow from browser to a WAS cluster through IHS.**  
The client resolves the application FQDN and connects to IHS, usually through a load balancer. IHS receives HTTP/HTTPS traffic and passes application requests to the WebSphere plug-in. The plug-in reads `plugin-cfg.xml`, matches the URI and virtual host, selects a healthy cluster member and forwards the request over the configured HTTP or HTTPS transport. The response returns through IHS to the client.

**2. What is the role of the WebSphere web-server plug-in?**  
It connects the external web server to WAS. It performs URI-based routing, cluster member selection, load balancing and failover based on the generated plug-in configuration.

**3. What is `plugin-cfg.xml`?**  
It is the generated routing configuration used by the plug-in. It contains application URI groups, virtual hosts, cluster members, transport hostnames/ports and routing-related settings.

**4. Why is the IHS host added as an unmanaged node?**  
The IHS host does not run a WAS node agent or application-server profile. The unmanaged-node object represents it in the cell, while the IHS Administration Server provides supported remote administration for IBM HTTP Server.

**5. Do we install a WAS node agent on the IHS server?**  
No, not for this remote unmanaged-node topology. The IHS Administration Server is used for supported remote IHS management.

**6. What is the difference between IHS and the WebSphere plug-in?**  
IHS is the web server that accepts client connections and serves web content. The plug-in is an IHS module that routes application requests to WAS.

**7. What is the difference between Generate Plug-in and Propagate Plug-in?**  
Generate creates the current `plugin-cfg.xml` from the WAS cell configuration. Propagate transfers that generated file to the remote web-server host.

**8. When should the plug-in configuration be regenerated?**  
After application deployment/removal, context-root or virtual-host changes, cluster membership/transport changes, or plug-in property changes that affect routing.

**9. What is the purpose of the IHS Administration Server?**  
It provides a remote management endpoint so the WAS console can perform supported IHS administration tasks such as start/stop, view logs and manage configuration. It is separate from the public IHS listener.

**10. Why must the IHS Admin Server credentials match the WAS web-server definition?**  
The WAS console authenticates to the IHS Admin Server using the credentials stored in the IHS `admin.passwd` file. A mismatch prevents remote administration and propagation.

### SSL/TLS and security

**11. Explain the two TLS connections in this architecture.**  
Client-to-IHS TLS protects the browser/client connection. IHS plug-in-to-WAS TLS protects the backend connection. Each has its own endpoint certificate, trust configuration and troubleshooting path.

**12. If HTTPS works from the browser to IHS but the application returns 500/503, what do you check?**  
I check `http_plugin.log`, the backend WAS HTTPS transport, plug-in KDB trust, certificate chain/expiry, hostname validation, TLS protocol/cipher compatibility, firewall and backend port reachability.

**13. What is `plugin-key.kdb` used for?**  
It is the CMS key database used by the WebSphere plug-in for SSL/TLS trust and, where configured, client certificate material when connecting to secure WAS transports.

**14. What is the purpose of a `.sth` file?**  
It is a GSKit stash file that stores protected access information for the key database so the plug-in can access it non-interactively. It must be protected like a credential.

**15. How do you renew an IHS SSL certificate?**  
Create or use the approved KDB, generate a CSR, obtain the signed certificate and chain, import the chain and personal certificate with the correct label, validate the KDB, update the IHS SSL configuration if required, test syntax, restart/reload in the change window and validate the public certificate.

**16. Does installing an IHS certificate automatically secure IHS-to-WAS traffic?**  
No. It secures the client-to-IHS endpoint. Backend TLS must be separately configured on WAS and trusted by the plug-in.

**17. What happens if the WAS certificate issuer is missing from the plug-in KDB?**  
The TLS handshake can fail because the plug-in cannot validate the WAS server certificate chain. I verify the issuer/intermediate chain and add the correct signer certificates to the plug-in KDB, then propagate and retest.

**18. How do you secure IHS administration?**  
Restrict the admin port to the DMGR/admin network, use strong unique credentials, use HTTPS for administration when required, protect `admin.passwd`, limit filesystem permissions and use least-privilege OS access.

### Production troubleshooting

**19. Users receive 404 through IHS, but the direct WAS URL works. What do you check?**  
I check application mapping to the web server, context root, virtual-host aliases, `WebSpherePluginConfig` path and whether the latest plug-in XML was generated and propagated.

**20. Users receive 503 through IHS. What is your approach?**  
I check the plug-in log for routing/connection errors, confirm cluster members are started, test backend ports from IHS, validate firewall/DNS and correlate with WAS logs.

**21. IHS is running but requests do not reach WAS. What do you check?**  
I verify the plug-in module is loaded, the plug-in configuration directive points to the correct XML, the XML contains the application route, and IHS can reach the backend member ports.

**22. Plug-in propagation fails from the WAS console. How do you troubleshoot?**  
I check Admin Server process/port, DMGR-to-IHS network access, hostname and protocol settings, `admin.passwd` credentials, file permissions and IHS Admin Server/WAS logs. If necessary, I use a controlled manual transfer as a documented fallback.

**23. Only one cluster member receives traffic. What could cause this?**  
The other member may be stopped, unreachable, misconfigured, missing from generated plug-in XML, or failing health/connection checks. I compare each member's host, transport port, firewall, application state and logs.

**24. What is your approach to a sudden increase in response time?**  
I establish whether latency is at the client/load balancer, IHS, network, plug-in or WAS layer. I correlate access logs, plug-in logs, CPU/memory, thread pools, connection pools, JVM/GC, database and network metrics before changing tuning parameters.

**25. Which logs are most important?**  
IHS `access_log` and `error_log`, plug-in `http_plugin.log`, IHS Administration Server logs, and WAS `SystemOut.log`/`SystemErr.log`. I correlate timestamps and request IDs where available.

### Leadership, change and operations

**26. How would you plan this implementation as a lead?**  
I start with compatibility and architecture review, map dependencies and firewall flows, confirm certificates and service accounts, agree application mappings, prepare implementation/validation/rollback plans, assign team owners and define acceptance criteria before the window.

**27. What are your go/no-go criteria?**  
Supported product combination, healthy DMGR and WAS cluster, approved network access, valid certificates, successful IHS syntax test, successful admin connectivity, generated/propagated plug-in file and a tested rollback path. A failed critical prerequisite is a no-go.

**28. How do you minimize production risk?**  
I use a peer-reviewed change, backup configuration and keys, add IHS to the load balancer in a controlled manner, validate with a limited traffic pool/canary where possible, monitor closely and keep the old route available until acceptance.

**29. What would you do if the change fails midway?**  
I stop further changes, assess user impact against the rollback trigger, drain the new IHS route, restore the last known-good configuration, verify the previous route, communicate status and preserve logs for root-cause analysis.

**30. How do you handle a disagreement between application and infrastructure teams during an outage?**  
I establish a shared timeline and evidence, separate symptoms from assumptions, assign parallel checks by layer, keep one incident lead and communicate impact/actions/next update clearly. I make changes only with the required approval and document the decision.

**31. What should be included in the operational handover?**  
Architecture and ports, server/account ownership, start/stop procedures, plug-in generation/propagation steps, certificate renewal, patching, log paths/rotation, monitoring thresholds, common troubleshooting, escalation matrix and rollback instructions.

**32. How do you decide whether to use `ALL` or `None` for application mapping?**  
I use `ALL` only when every eligible application is intended to be exposed through that web server and the security design supports it. In a production cell with multiple security domains or selective exposure requirements, I choose `None` and map approved applications individually.

**33. What metrics would you monitor after go-live?**  
Request rate, response time, HTTP status codes, active connections, IHS CPU/memory, disk/log growth, plug-in connection errors, backend member availability, WAS thread-pool/heap/GC metrics and certificate expiry.

**34. How do you handle a certificate expiry incident?**  
I identify whether the expired certificate is client-facing or backend trust-related, confirm impact and expiry chain, coordinate with PKI/security, renew/import the correct certificate, propagate trust material if needed, perform a controlled restart and verify the complete request path.

**35. What is your responsibility as lead after a successful change?**  
I obtain business and operations sign-off, monitor the environment, update CMDB/diagrams/SOPs, close actions, hand over support ownership and capture lessons learned.
